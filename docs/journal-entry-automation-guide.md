# 新人向けガイド：経理「仕訳入力業務」の効率化を受託したときの進め方

> 想定：顧客（事業会社の経理部門）から「仕訳入力を効率化したい」というテーマを受け取り、
> ベンダーである私たちが **検証（PoC）→ 実装 → 運用定着** までを担当する。
>
> LayerX（バクラク / Ai Workforce）と Algomatic のエンジニアブログ・登壇資料で公開されている
> 考え方を土台に、新人がそのまま使える「順番」と「注意点」に整理したものです。
> 各社の記事は末尾の「参考資料」にまとめています。

---

## 0. まず全体像（1枚で）

```
① 目的を握る ─→ ② 現状業務を知る ─→ ③ データと「正解」を用意する
                                                │
⑥ 本番実装 ←─ ⑤ Go/No-Go 判断 ←─ ④ 小さく検証する（PoC）
   │
   └─→ ⑦ 運用して賢くし続ける（修正データを学習に戻す）
```

覚えておく原則は3つだけです。

1. **AIは100%正解しない。だから「間違えても困らない業務の流れ」ごと設計する**
   （LayerX「LLMの不確実性との付き合い方」）
2. **評価できないものは改善できない。最初に「何をもって正解か」を決める**
   （LayerX「評価駆動開発」「評価なくしてAIエージェント開発なし」）
3. **作って終わりではなく、使われるほど賢くなる仕組みにする**
   （LayerX「使えば使うほど賢くなるAI機能」）

## 1. 前提知識：仕訳入力業務ってそもそも何をしているの？

### 用語ミニ辞典

| 用語 | ざっくり意味 |
|---|---|
| 仕訳 | 取引を「借方 / 貸方」の2つの側面に分けて記録すること |
| 勘定科目 | 通信費・旅費交通費・消耗品費などの分類ラベル |
| 補助科目 / 部門 | 勘定科目をさらに細かく分けるラベル（会社ごとに自由に作れる） |
| 税区分 | 課税仕入10% / 8%（軽減）/ 非課税 / 不課税 など |
| 証憑（しょうひょう） | 請求書・領収書・明細など、取引の証拠書類 |
| 適格請求書（インボイス） | 登録番号のある請求書。仕入税額控除の可否に影響する |
| 月次決算 / 締め | 毎月の数字を確定させる作業。仕訳が遅れると締めが遅れる |

### 仕訳の例

AWSから 110,000円（税込）の請求書が届いた場合（税抜経理の例）：

| 借方 | 金額 | 貸方 | 金額 |
|---|---|---|---|
| 通信費 | 100,000 | 未払金 | 110,000 |
| 仮払消費税（課税仕入10%） | 10,000 | | |

### 実際の業務の流れ（典型）

```
証憑が届く（紙/PDF/メール）
 → 内容を読む（取引先・日付・金額・税率・明細）
 → 勘定科目・部門・税区分を判断する
 → 会計ソフトに入力（またはCSV取込）
 → 上長・経理責任者が確認・承認
 → 支払・月次締め
```

**ポイント**：効率化の対象は「入力」だけではありません。
「読む」「判断する」「確認する」のどこに時間がかかっているかで、打つ手がまったく変わります。

## 2. 実施ステップ詳細

### ステップ① 目的とゴールを顧客と握る（キックオフ）

**やること**
- 顧客が困っていることを **業務の言葉で** 言語化する
  - 例：「月次締めに8営業日かかる。仕訳入力に担当者3人で月120時間」
- ゴールを **数字** で合意する（KPI）
  - 処理時間（件あたり / 月あたり）
  - 自動化率（人が修正せずに通った仕訳の割合）
  - 誤り率（後工程で差し戻された割合）
  - 締め日数
- 体制と役割を決める：顧客側に **経理の実務担当者**（正解を判断できる人）を必ず入れてもらう

**注意点**
- 「AIで何かしたい」から始めない。**「どの業務の、どの時間を、どれだけ減らすか」** に落とす。
- 「100%自動化」を約束しない。LayerX も自動化を **段階（レベル）** で捉えており、
  まずは「AIが下書き、人が確認」から始めるのが現実的です。
- 費用対効果の見積もり軸（工数削減 × 人件費 vs. 開発・API費用）を最初から意識する。

---

### ステップ② 現状業務（As-Is）を把握する

**やること**
- 業務担当者へのヒアリング＋ **実際の作業を横で見る（業務観察）**
- 業務フロー図を書く（誰が・何を見て・何を判断し・どこに入力するか）
- 仕訳を **パターン分類** して、件数と手間を数える

| 観点 | 例 |
|---|---|
| 証憑の種類 | 請求書 / 領収書 / 経費精算 / 銀行明細 / カード明細 |
| 定型度 | 毎月同じ（家賃・SaaS）vs. 毎回違う（外注・備品の明細多数） |
| 判断の難しさ | 取引先で科目が決まる vs. 明細の中身を見ないと決まらない |
| 明細行数 | 1行 vs. 数十行（按分・部門配賦あり） |
| 例外 | 前払・立替・按分・海外通貨・軽減税率混在 |

- 顧客固有のルールを集める：勘定科目マスタ、部門・補助科目マスタ、税区分、社内の経理規程、会計ソフトの取込フォーマット

**注意点**
- **「件数が多い × 判断が単純」から攻めるのが鉄則**。いきなり一番難しい業務を狙わない。
- LayerX の事例では、従来の「取引先ごとに過去仕訳を補完」する方式では、
  **明細が多く毎回中身が変わる請求書** は人手入力が残っていた。
  → これが LLM で新たに解ける領域（AI明細仕訳）。つまり **「ルールで解ける部分」と「LLMが必要な部分」を切り分ける** のが大事。
- 勘定科目や補助科目は **会社ごとに自由に作られる**。
  LayerX の経費科目推薦でも、テナントごとに科目体系が違うため単純な分類問題として解けず、推薦問題として設計している。
  → 汎用モデルをそのまま当てても合わない前提で考える。
- ヒアリングで聞いた話と実際の作業は違うことが多い。**必ず実物（証憑と会計データ）を見る**。

---

### ステップ③ データを集め、「正解」と評価方法を決める

ここがプロジェクトの成否を分けます。

**やること**
1. **データ収集**：過去の「証憑 ＋ 実際に登録された仕訳」のペアを数か月〜1年分もらう
2. **評価データセット作成**：代表的なパターン・難しいパターン・例外をバランスよく選ぶ
   - LayerX は本番データをもとに Langfuse の Datasets 機能で評価用データセットを構築している
3. **評価指標を決める**

| 指標 | 意味 | 使いどころ |
|---|---|---|
| 項目別正解率 | 科目・部門・税区分・金額それぞれの一致率 | どこが弱いかの特定 |
| 仕訳完全一致率 | 全項目が合っている割合 | 「そのまま通せる」割合の目安 |
| 自動化率 | 人が修正せずに承認した割合 | 業務効果に一番近い |
| カバレッジ | AIが「回答した」割合（保留を除く） | 精度とのトレードオフ管理 |
| 処理時間・コスト | 1件あたりの所要時間・API費用 | 費用対効果 |

**注意点**
- **過去の仕訳＝正解とは限らない**。担当者ごとの判断の揺れ、単純ミスが混ざっている。
  LayerX も Confident Learning でラベル（正解データ）の誤りを見つけて品質改善する取り組みを公開している。
  → 怪しいデータは顧客の経理担当者に確認し、**「正解の定義」自体を顧客と合意** する。
- 「精度」は **様々な切り口でモニタリング** する（取引先別・証憑種類別・項目別など）。
  LayerX の AI-OCR でも、多面的な精度モニタリングでボトルネックを可視化し、「勘ではなく事実で」改善している。
- 経理データは **機密情報**。データの受け渡し方法、保管場所、マスキング、外部LLM APIへの送信可否を
  契約・セキュリティ部門と事前に確認する（必要ならローカルLLM／閉域環境も選択肢。Algomatic もセキュアなLLM導入支援を提供している）。

### ステップ④ 小さく検証する（PoC）

**やること（推奨の順番）**

1. **ベースラインを作る**：まずはAIを使わない方法で測る
   - 例：取引先名 → 前回と同じ科目、キーワードルール
   - ここで既に7割解けるなら、LLMは残り3割に集中させればよい
2. **読み取り（OCR/抽出）と判断（科目推定）を分けて検証する**
   - 「読み間違い」なのか「判断間違い」なのかを切り分けられるようにする
3. **LLM / 機械学習で判断部分を作る**
   - 入力：証憑の抽出結果 ＋ その会社の科目マスタ ＋ 過去の類似仕訳
   - 出力：科目・部門・税区分 ＋ **自信度** ＋ 根拠
4. **評価データセットで回して、エラーを分析する**
   - 間違いを1件ずつ見て、**誤りのパターンを言葉にする**（Algomatic の品質保証の考え方）
   - 例：「軽減税率8%と10%が混在した明細で税区分を取り違える」
5. **改善 → 再評価** を回す（プロンプト変更のたびに全件で回帰テスト）

**効く工夫（両社のブログより）**
- **生成と評価を分ける**：仕訳を作るステップと、それをチェックするステップを別にする（Algomatic）
- **自信がないときは「判断保留」にして人に回す**：無理に答えさせない（Algomatic）
- **動作検証（Behavioral Testing）**：意味が同じ入力（表記ゆれ、全角半角、明細の順序違い）で結果がブレないかチェックリストで確認する（Algomatic）
- **複数回サンプリング・E2Eでの検証を怠らない**：LLMは同じ入力でも出力が揺れ、プロンプト修正の影響範囲が読みにくい（LayerX）
- **難しい工程だけ強いモデルを使う**：LayerX は非定型見積書の明細抽出で、差分比較・再推論ステップに高性能モデルを使うなど使い分けて精度を約80%→約95%に改善

**注意点**
- PoC で「デモがうまく動いた」は成功ではない。**事前に決めた評価データと指標で数字を出す**。
- 長い明細の取り漏れ、罫線のない表のズレ、スキャン品質の低い書類の誤読、不要行の混入は **よく起きる失敗**（LayerX）。評価データに必ず入れておく。
- 速度・コストも測る。精度が高くても1件数十秒・数十円では業務に乗らないことがある。

### ステップ⑤ Go / No-Go を判断する

**やること**
- PoC結果を顧客に報告：指標の数値、得意・苦手なパターン、想定効果（時間削減）、残る人手作業、費用
- **どの範囲を自動化し、どこを人に残すか** を合意する
  - 例：「定型の請求書は自動化率90%を目標、非定型は下書き提案まで」

**注意点**
- 合格基準は **PoCを始める前に** 合意しておく（後出しにすると揉める）。
- 苦手領域を正直に伝える。「全部いける」より「ここまでは確実」の方が信頼される。

---

### ステップ⑥ 本番実装（To-Be の業務に組み込む）

**業務設計（ここが一番大事）**
- **Human-in-the-loop を前提にする**：AIが下書き → 人が確認・修正 → 承認
- **AIの間違いをリカバリーしやすくする**（LayerX）
  - 候補を編集可能な形で出す、ドロップダウンで修正できる、根拠（どの明細・どの過去仕訳を参考にしたか）を表示する
  - 自信度が低いものだけを目立たせ、人の確認を集中させる
- LLMの誤りが業務に与える悪影響は **体験設計次第**。後工程（承認・支払・締め）まで含めて設計する（LayerX）

**システム面**
- 会計ソフトとの連携（API / CSV取込フォーマット）、マスタの同期
- **ログとトレース**：入力・プロンプト・出力・人の修正を全部記録する（LayerX は Langfuse を LLMOps 基盤として利用）
- **プロンプトのバージョン管理** と、変更時の **自動回帰テスト**（評価データセットで再採点）
- 監査対応：誰が（AIか人か）いつ何を確定したかの証跡を残す
- 障害時のフォールバック（AIが止まっても手入力で業務が回る）

**注意点**
- 段階リリース：一部の取引先・一部の担当者から始め、数字を見ながら広げる。
- 経理は月次サイクル。**締め直前のリリースは避ける**。

---

### ステップ⑦ 運用して「使うほど賢く」する

**やること**
- **人の修正をデータとして回収し、定期的に学習・改善に戻す**
  - LayerX は、ユーザーが負担なく修正できるUI（候補のドロップダウン表示）で構造化された修正データを集め、
    定期的にパイプラインで更新することで「使えば使うほど賢くなる」AI機能を実現している
- 精度ダッシュボードで定点観測（自動化率・修正率・項目別の誤り）
- 月次で顧客と振り返り（効果測定と次の改善対象の決定）

**注意点**
- **変化に弱い**ことを忘れない：勘定科目マスタの変更、組織変更（部門）、新しい取引先、税制・インボイス制度・電子帳簿保存法の改正、決算期の特殊仕訳。
- 精度が落ちたら「モデルのせい」と決めつけず、まず **入力データやマスタが変わっていないか** を見る。

## 3. 注意点まとめ（新人がハマりやすいところ）

| # | ハマりどころ | 対策 |
|---|---|---|
| 1 | 目的が曖昧なまま作り始める | KPIを数字で合意してから着手 |
| 2 | 業務を見ずに想像で設計する | 実物の証憑・会計データ・作業を見る |
| 3 | 過去仕訳をそのまま正解扱い | 正解の定義を顧客と合意、ノイズを除去 |
| 4 | デモが動いたので成功と判断 | 評価データセットと指標で判断 |
| 5 | 平均精度だけ見る | 取引先別・項目別・証憑別に分解して見る |
| 6 | 100%自動化を約束する | 段階的な自動化レベルと人の確認を前提にする |
| 7 | AIの間違いが後工程に流れる | 自信度・保留・修正しやすいUIでリカバリー設計 |
| 8 | プロンプトを場当たり的に直す | 変更ごとに全件回帰テスト、バージョン管理 |
| 9 | 機密データを安易に外部APIへ | 契約・セキュリティ確認、マスキング、閉域も検討 |
| 10 | リリースして終わり | 修正データを回収し継続改善、変化を監視 |

## 4. すぐ使えるチェックリスト

**キックオフ**
- [ ] 解決したい業務課題と数値目標（KPI）を合意した
- [ ] 顧客側の経理実務担当者がプロジェクトに参加している
- [ ] データの取り扱い（受け渡し・保管・外部API利用可否）を確認した

**現状把握**
- [ ] 業務フロー図を作り、顧客にレビューしてもらった
- [ ] 仕訳をパターン分類し、件数と工数を数えた
- [ ] 科目・部門・税区分マスタ、経理規程、会計ソフトの取込仕様を入手した

**評価準備**
- [ ] 評価データセット（代表＋難所＋例外）を作った
- [ ] 正解の定義と評価指標、合格基準を顧客と合意した

**PoC**
- [ ] AIなしのベースラインを測った
- [ ] 抽出と判断を分けて評価した
- [ ] エラーを1件ずつ見て、誤りパターンを言語化した
- [ ] 同じ意味の入力で結果がブレないか確認した
- [ ] 速度とコストを測った

**本番**
- [ ] 人の確認・修正・承認フローを設計した
- [ ] 自信度・根拠・保留の仕組みを入れた
- [ ] ログ／トレース、プロンプト管理、回帰テストを用意した
- [ ] 監査証跡とフォールバックを用意した

**運用**
- [ ] 修正データを回収して改善に戻す仕組みがある
- [ ] 精度ダッシュボードと月次振り返りの場がある
