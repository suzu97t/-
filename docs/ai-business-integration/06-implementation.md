# 06 本番実装：業務の流れごと作る

[← 目次へ](./README.md) ｜ 前：[05 Go/No-Go 判断と報告](./05-decision.md)

> **この章のゴール**
> - 人とAIの役割分担のパターンを知り、業務に合ったものを選べる
> - 「AIが間違えても困らない」業務の流れと画面を設計できる
> - 本番で必要な仕組み（ログ、回帰テスト、監査証跡、障害時の代替）を漏れなく挙げられる
> - 安全にリリースし、現場に定着させる手順を説明できる

---

## 1. PoCと本番の違い

| 観点 | PoC | 本番 |
|---|---|---|
| 目的 | 判断材料を集める | 毎日の業務を回す |
| 入力 | 選んだ評価データ | 何が来るか分からない |
| 失敗したとき | 結果が悪いだけ | **後工程（お金、顧客、法令）に影響** |
| 使う人 | 開発メンバー | 現場の担当者（AIに詳しくない） |
| 期間 | 数週間 | 何年も（ルール・マスタ・担当者・モデルが変わる） |

→ 本番では、**AIの精度そのものより「業務の流れ」「画面」「運用の仕組み」の作り込みが大半** を占めます。

---

## 2. 人とAIの役割分担を設計する

### 4つの基本パターン

| パターン | 流れ | 向いているケース | 自動化レベル |
|---|---|---|---|
| **A. 下書き型** | AIが案を作る → 人が全件確認・修正 → 確定 | 始めたばかり、誤りの影響が大きい | L2 |
| **B. 振り分け型** | AIが処理し、自信のあるものは自動、怪しいものだけ人へ | 件数が多く、型によって難しさが違う | L3 |
| **C. 事後チェック型** | 人が処理し、AIが誤り・漏れを指摘する | 人の判断を残したい、品質向上が目的 | ― |
| **D. 自動＋抜き取り型** | AIが処理して確定、人は例外と抜き取り検査だけ | 実績が十分にあり、誤りの影響が小さい型 | L4 |

- 1つの業務の中で、**ケースの型ごとにパターンを変えてよい**
- 最初は A か B から始め、実績データで安全を確かめた型から D に近づける（→ [00 自動化のレベル](./00-concepts.md#5-自動化のレベル)）
- **社外に直接出るもの（顧客への返信、支払、契約）は、人の確認を外すのに特に慎重に**

### 間違いから回復しやすい流れにする

LayerX の「LLMの不確実性との付き合い方」では、

- LLMの誤りが業務に与える悪影響は **体験設計次第** である
- だから精度に加えて、**後工程への影響** に注意する
- **LLMの間違いからリカバリーしやすいワークフロー** にする（例：網羅的に出力し、編集可能な形にする）

と整理しています。具体的には：

| 設計の工夫 | なぜ |
|---|---|
| AIの出力は「案」として編集可能な状態で出す | 間違っていてもその場で直せる |
| 要確認のものを目立たせ、自動OKのものと分ける | 人の注意を必要なところに集中させる |
| 根拠（参照した事例・ルール）を横に表示 | 確認が速く、誤りに気付きやすい |
| 入力の実物と出力を並べ、該当箇所をハイライト | 読み取りミスに気付ける |
| 確定前に人の目を通す（パターンA・B） | 誤りが後工程に流れない |
| 確定後も取り消し・修正できる | 後で見つかっても直せる |

> 📘 **ケーススタディ：仕訳入力の場合**
> 明細が多い請求書は **パターンB**（7割は一覧で一括承認、3割を担当者が確認）、
> 源泉・外貨などの特殊ケースは **パターンA**（全件確認）、
> 毎月定額の請求書は AIを使わずルールで処理し、月次で抜き取り確認。

### 責任分界を明文化する

| 項目 | 責任者 |
|---|---|
| 案の作成 | システム（AI） |
| 確定・承認 | 顧客の担当者・承認者 |
| 判断ルール・マスタの維持 | 顧客の業務部門（当社は支援） |
| システムの稼働・精度の監視 | 当社（保守契約の範囲） |

## 3. 画面の設計

現場の担当者が毎日何百件も見る画面です。**クリック数と目の移動を減らす** ことが、そのまま効果になります。

### 原則

- **入力の実物とAIの出力を並べる**（左右に配置、対応箇所をハイライト）
- **修正は選択式（ドロップダウン）を基本にする**。自由入力だとマスタにない値やゆれが混入し、修正データも改善に使いにくい
  - LayerX は、ドロップダウンで候補を表示してユーザーが負担なく修正できるようにし、その **構造化された修正データ** を集めて定期的にモデルを更新する仕組みを紹介しています（→ [07](./07-operation.md)）
- 候補の並び順は「AIの推奨 → この相手で過去に使ったもの → その他」
- **要確認の理由を表示する**（「10万円以上の物品です」「過去と違う判断です」）
- キーボードだけで操作できる、要確認だけを順に見られる

> 📘 **ケーススタディ：仕訳入力の場合** の確認画面
> ```
> ┌───────────────────────┬────────────────────────────────────┐
> │ 請求書の画像            │ 仕訳案   取引先: 事務用品通販B社            │
> │ 1 トナー   24,000  ←─── │ 1 消耗品費 ▼ 営業部 ▼ 10% ▼ 24,000   ✓  │
> │ 2 チェア  128,000  ←─── │ 2 工具器具備品 ▼ 物流部 ▼ 10% ▼ 128,000 ⚠│
> │                       │   ⚠ 10万円以上の物品です（R-001）         │
> │                       │   根拠: 過去仕訳 2026-03 チェア→備品       │
> │                       │ 合計 152,000 ＝ 請求書合計 152,000 ✓    │
> │                       │ [承認] [差し戻し] [次の要確認へ]           │
> └───────────────────────┴────────────────────────────────────┘
> ```

### 作る前に現場に触ってもらう

画面のモックアップ（紙芝居）の段階で、実務担当者に **実際のデータで操作してもらいます**。
「この順番では見ない」「ここにこの情報も出してほしい」という指摘は、作る前に貰うほど安く済みます。

## 4. システム構成と要件

```
 入力の入口          AI処理                          確認・確定          後工程
 ─────────         ────────                        ─────────         ────────
 メール・フォルダ ─┐  ┌→ ①読み取り                      確認画面           登録先システム
 既存システム    ─┼→ ┼→ ②参考情報の検索  → 案のDB →  （人が確認・修正） →  （CSV/API）
                ─┘  └→ ③判断・生成 → ④チェック → ⑤振り分け      │
                           ↑                                     ↓
                     マスタ・判断ルール集                    修正ログ → 改善（07）
```

### 要件定義チェックリスト

**連携**
- [ ] 入力の取り込み方法（メール、フォルダ監視、既存システムのAPI）
- [ ] 後工程への連携方法（CSV、API）と、連携エラー時の扱い
- [ ] マスタの同期方法と頻度
- [ ] 二重処理の防止（同じ入力が2回届いた場合）

**品質・運用（LLMOps）**
- [ ] すべての処理の **ログ（トレース）**：入力、プロンプトのバージョン、モデル、出力、処理時間、費用
- [ ] **プロンプトのバージョン管理**：いつ・誰が・何を変えたか
- [ ] **回帰テスト**：プロンプト・モデル・ルールを変えたら評価データで自動採点し、基準を下回ったらリリースしない
- [ ] モデルの提供元がモデルを更新・廃止したときの移行手順（新しいモデルで再評価してから切り替え）

> LayerX は Langfuse を LLMOps の基盤として採用し、プロンプトをプロダクトのコードとは独立して管理しつつ、
> データセットを使った自動的な回帰テストや独自の評価基準での採点を行っていると紹介しています。

**セキュリティ・統制**
- [ ] データの保存場所と暗号化、アクセス権限
- [ ] 外部LLM APIの利用条件（学習に使われない契約・設定、保存期間、リージョン）
- [ ] 個人情報のマスキング
- [ ] プロンプトインジェクション対策とそのテスト
- [ ] **監査証跡**：どれを、AIが提案し、誰が修正・承認し、いつ後工程に渡したか
- [ ] 業界・業務固有の法令要件（仕訳入力なら電子帳簿保存法など）

**障害・例外**
- [ ] AIが止まったとき（API障害、利用上限）でも、**従来どおり人の手で業務が回る** こと
- [ ] 処理の遅延・失敗の通知
- [ ] 費用の上限（異常な大量処理で請求が膨らまないように）

## 5. テスト

| テスト | 内容 | 誰が |
|---|---|---|
| 単体・結合テスト | 部品ごと・つないだときに正しく動くか | 当社 |
| 評価データでの回帰テスト | PoCと同等以上の精度が出るか | 当社 |
| 頑健性テスト | [04 の動作検証](./04-poc.md#8-step-6速度コスト揺れ頑健性を測る) を自動テストにする | 当社 |
| 受入テスト | 実際の業務シナリオで、現場の担当者が操作して確認 | 顧客（当社が支援） |
| 連携テスト | 後工程のシステムに正しく渡り、結果が合うか | 顧客＋当社 |

## 6. リリースの進め方（いきなり全部切り替えない）

```
 Phase 1 並行稼働（シャドー運用、2〜4週間）
   AIは裏で案を作るが、担当者は従来どおり作業。後でAIの案と人の結果を比べて、本番データでの精度を測る
     ↓ 本番データで合格基準を満たすことを確認
 Phase 2 限定開始
   対象を絞って（ケースの型、担当者1名など）、AIの案を確認・修正する運用に切り替える
     ↓ 問題がなければ
 Phase 3 拡大
   対象の型・担当者を広げる
     ↓
 Phase 4 自動化レベルを上げる
   実績が溜まった型は確認を簡略化する（例：3か月連続で修正ゼロの型は一括承認に）
```

- **並行稼働で、本番データでの精度を必ず確かめる。** 評価データと本番では分布が違う
- **繁忙期・締め直前にはリリースしない**
- 自動化レベルを上げるのは、**実績データで根拠を示してから**

## 8. 現場への定着

技術的に完成しても、**現場が使わなければ効果はゼロ** です。

| よくある反応 | 背景 | 対応 |
|---|---|---|
| 「AIは信用できない。全部自分で確認する」 | 誤りへの不安、責任への不安 | 精度の実績を数字で共有する。要確認以外は抜き取りで良い、という運用ルールを責任者に決めてもらう |
| 「前のやり方の方が速い」 | 画面が使いにくい、慣れていない | 操作ログで詰まっている所を見つけて直す。慣れるまでの期間を見込む |
| 「仕事を奪われるのでは」 | 将来への不安 | 目的（残業削減、判断が必要な仕事に時間を使う）を責任者から伝えてもらう |
| 「AIの間違いを直すのが面倒」 | 修正の手間、直しても良くならない | 修正しやすい画面、修正が改善に反映されたことを見せる |

- **現場の担当者をPoCの段階から巻き込む**（正解確認会、画面の試用）。自分が作りに関わったものは使ってもらえる
- **効果を本人たちに見せる**（「先月より月○時間減りました」）
- 確認が形だけになる **自動化バイアス**（AIの案が大体正しいと、人の確認が雑になる）に注意。要確認を絞り、そこは確実に見てもらう。定期的に自動OKのものを抜き取り検査する

## 10. 注意点

- **AIの精度より、業務の流れと画面の方が効果を左右する。**
- **自動で通す範囲は、本番データの実績で決める。** PoCの数字だけで広げない。
- **ログが残っていないと、後から何も分からない。** 「なぜこの結果になったか」を後で追えることが、改善にも監査にも必須。
- **人の手に戻せる状態を必ず残す。** AIが止まっても業務が止まらないように。
