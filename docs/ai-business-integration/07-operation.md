# 07 運用・継続改善：使うほど賢くする

[← 目次へ](./README.md) ｜ 前：[06 本番実装](./06-implementation.md)

> **この章のゴール**
> - 本番稼働後に、何を・どの頻度で見ればよいか分かる
> - 人の修正を改善につなげるサイクルを回せる
> - 精度が落ちたときに、原因を順番に切り分けられる

---

## 1. 「使えば使うほど賢くなる」仕組み

LayerX は「AI Agent時代における『使えば使うほど賢くなるAI機能』の開発」で、次のような仕組みを紹介しています。

- ユーザーが負担なく修正できるUI（ドロップダウンでの候補表示）で、**構造化された修正データ** を集める
- そのデータを使って、**定期的にモデル・データを更新** する（パイプラインで自動化）
- 結果として、各社の使い方に合わせて精度が上がっていく

どの業務でも、本番で毎日次のデータが溜まります。これは **本番の正解データ** そのものです。

```
入力ID / AIの出力 / 人が確定した値 / 修正したか / 修正した人 / 日時 / 要確認だったか
```

| 使い方 | 頻度 | 内容 |
|---|---|---|
| 参考事例の更新 | 毎日〜毎週 | 確定した結果を「過去の事例」として次の判断に使う |
| 誤りパターンの発見 | 毎月 | 修正が多いケース・項目を集計し、エラー分析（[04](./04-poc.md#6-step-4エラー分析いちばん大事な作業)と同じやり方） |
| 判断ルール集の更新 | 毎月 | 同じ修正が繰り返されている → ルールとして明文化 |
| 評価データセットの更新 | 四半期 | 新しいケースを評価データに追加（新しいバージョンとして） |
| プロンプト・モデルの改善 | 必要に応じて | 改善 → 評価データで回帰テスト → リリース |

---

## 2. 何を見るか

### AIの品質の指標

| 指標 | 意味 | 見るべき変化 |
|---|---|---|
| 修正率 | 自動OKにしたもののうち、人が修正した割合 | 上がったら要注意（AIが自信を持って間違えている） |
| 要確認率 | 要確認に回った割合 | 上がると人の負担が増える。下がりすぎたら判定が甘くなっていないか確認 |
| 項目別・型別の修正率 | どこが崩れたか | 特定の項目・型だけ悪化していないか |
| 相手別の修正率 | 修正が多い取引先・顧客・書類の種類 | 書式変更・内容の変化 |
| 処理件数・処理時間・費用 | 日次・月次 | 異常な増加 |
| エラー件数 | 読み取り失敗、API障害 | ゼロでない日の原因 |

### 業務KPI（キックオフで決めたもの）

**AIの精度だけでなく、業務KPIを必ず追う。** 精度が上がっても業務KPIが変わっていなければ、どこか別の場所にボトルネックがあります。

> 📘 **ケーススタディ：仕訳入力の場合**：1件あたりの処理時間、月次決算の締め日数、月次チェックでの差し戻し件数を毎月確認。

### 抜き取り検査

自動OKで通ったものも、**毎月一定数（例：100件）を抜き取って人が見直します**。
確認を簡略化している部分の誤りは、修正率に現れないからです（気付かれないまま通っている可能性）。

---

## 3. 精度が落ちたときの切り分け手順

「AIの精度が落ちた」と言われたら、**いきなりプロンプトを直さない**。次の順で確認します。

```
1. 入力が変わっていないか？
   □ 特定の相手の書式が変わった
   □ 新しい相手・新しい種類の入力が急に増えた
   □ 入力の品質が変わった（スキャン設定、送られてくる形式）
2. マスタ・ルールが変わっていないか？
   □ 選択肢の追加・廃止・名称変更（組織変更、期首）
   □ 社内ルールの変更
   □ マスタの同期が止まっている
3. 制度・外部環境が変わっていないか？
   □ 法令・制度の改正
   □ 取引先・顧客側の変化
4. システムが変わっていないか？
   □ プロンプト・モデルのバージョンが変わった（意図した変更 or 提供元の更新）
   □ 参考事例の検索がおかしい
5. 正解の付け方が変わっていないか？
   □ 担当者が変わって、判断の仕方が変わった
6. ここまで問題なければ → AIの判断そのものの問題としてエラー分析
```

**多くの場合、原因は1〜3（入力・マスタ・制度の変化）** です。

> 📘 **ケーススタディ：仕訳入力の場合**
> 2026年10月にインボイス制度の経過措置（免税事業者からの仕入の控除割合）が80%から70%に変わった。
> → 税区分の判断ルールと、評価データの正解を見直す必要がある、という「3. 制度の変化」の典型例。

---

## 4. 定期的なイベントへの備え

どの業務にも、決まったタイミングでの変化があります。**年間カレンダーにして、事前に確認する** 運用にします。

| 種類 | 例 | AI側で確認すること |
|---|---|---|
| 組織・体制の変更 | 期首の組織変更、人事異動 | マスタ同期、判断ルールの更新 |
| 制度・法令の改正 | 施行日の多い4月・10月 | ルール更新、評価データの正解の見直し |
| 繁忙期 | 締め、決算、キャンペーン | リリース・メンテナンスをしない、監視を強める |
| 取引先・顧客側の変化 | 年度替わりの書式変更 | 修正率の監視を強める |

---

## 5. 月次の定例（顧客との振り返り）

**アジェンダの例（30〜60分）**

1. 業務KPIの推移
2. AIの品質指標の推移（修正率、要確認率）
3. 修正が多かったパターン上位3つと、対策
4. 判断ルール集に追加したい内容の確認（現場の担当者に正解を決めてもらう）
5. 自動化レベルを上げられる対象の提案（実績データ付きで）
6. 今後の予定（制度変更、組織変更、リリース予定）

---

## 6. 新人のタスク

- [ ] 品質指標の月次確認とレポート作成
- [ ] 修正データの集計（修正が多いケース・項目・パターン）
- [ ] 抜き取り検査の実施と記録
- [ ] 年間カレンダーの管理
- [ ] 月次定例の資料と議事録

---

## 7. 注意点

- **リリースして終わりにしない。** 放置すると、入力・マスタ・制度の変化で精度は必ず落ちていく。
- **修正データをそのまま正解として使わない。** 人の修正にも誤りやゆれがある。定期的にサンプルを確認する（[03](./03-data-and-eval.md#3-1-過去の記録--正解) と同じ）。
- **自動化レベルを上げるのは、データで根拠を示してから。**
- **顧客側の担当者が変わったら要注意。** 判断の仕方が変わる。引き継ぎ時に判断ルール集を使ってもらう。

---

## 完了チェック（運用が回っている状態）

- [ ] 修正データが自動で溜まり、参考事例・評価データの更新に使われている
- [ ] 品質指標と業務KPIを毎月確認している
- [ ] 抜き取り検査を毎月実施している
- [ ] 精度低下時の切り分け手順が文書化されている
- [ ] 年間カレンダーで変化に備えている
- [ ] 月次定例で、改善と自動化レベルの見直しを行っている
