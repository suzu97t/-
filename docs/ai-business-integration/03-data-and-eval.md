# 03 データと評価の設計

[← 目次へ](./README.md) ｜ 前：[02 現状業務の把握](./02-as-is.md)

> **この章のゴール**
> - 顧客に何のデータを、どの形式で、どう安全に貰うかを依頼できる
> - 「何をもって正解とするか」を顧客と合意できる
> - タスクの型に合った評価方法を選び、評価データセット・指標・合格基準を作れる
>
> **この章がプロジェクトの成否を分けます。** ここを雑にすると、PoCの結果が「良いのか悪いのか誰にも分からない」状態になります。

---

## 1. なぜ「評価」から先に作るのか

LLMを使ったシステムには、普通のプログラムと違う性質があります（→ [00](./00-concepts.md#7-llmならではの注意点全章で繰り返し出てきます)）。

- **同じ入力でも出力が揺れる**
- **プロンプトを1か所直すと、思わぬところが壊れる**
- **100%は正解しない**

LayerX はこれを踏まえ、**評価駆動開発（Eval-driven development）** を掲げています。
評価データと採点方法を先に用意し、変更のたびに全件で採点して、良くなったか悪くなったかを数字で確かめるやり方です。
Algomatic も、LLMの品質保証として **誤りのパターンを言語化し、人の検証で継続的に改善する** ことを重視しています。

```
×  作る → 触ってみる → なんとなく良さそう → 顧客に見せる → 「ここ違うね」 → 直す → 別のところが壊れる …
○  評価データを作る → 作る → 全件採点 → 誤りを分析 → 直す → 全件採点（悪化していないか確認）→ …
```

## 2. データを貰う

### 2-1. 依頼するデータ（どの業務でも基本は同じ）

[templates/data-request.md](./templates/data-request.md) に依頼書のひな形があります。

| データ | 用途 | 量の目安 |
|---|---|---|
| **過去の処理結果**（人が作った成果物の記録） | 正解、参考データ、集計 | 6〜12か月分 |
| **その元になった入力**（書類・メール・データ） | AIの入力 | 評価用に300〜500件分 |
| 入力と処理結果の対応表 | どの入力からどの結果ができたか | 上記と同じ |
| マスタ（選択肢の一覧） | AIが選べる選択肢 | 全件 |
| 規程・マニュアル・判断基準 | AIに渡す判断ルール | あるだけ |
| 担当者が判断に使っている資料 | 同上 | あるだけ |

> 📘 **ケーススタディ：仕訳入力の場合**
> 過去の処理結果 ＝ 会計ソフトの仕訳データ（CSV）、入力 ＝ 請求書PDF、
> マスタ ＝ 勘定科目・部門・税区分・取引先、規程 ＝ 経理規程と取引先ごとの科目対応表。

### 2-2. 「入力と結果の対応」が一番の難所

処理結果の記録はすぐ出ても、**どの結果がどの入力から作られたか** が辿れないことがよくあります。

- システムにIDで紐付いている → 楽
- 共有フォルダにファイル名で保存している → 名寄せスクリプトで対応付け、最後は目視
- 紙で保管・記録がない → 評価用の300件だけ用意してもらう、または新しく正解を付けてもらう

→ キックオフ直後に **「どうやって対応付けるか」を情シス・現場と相談** してください。ここで2〜3週間溶けることがあります。

### 2-3. データの安全な扱い

業務データには、取引条件、個人情報、社外秘の情報が含まれます。

- [ ] データ取扱いの覚書（NDA・データ処理契約）を締結してから受け取る
- [ ] 受け渡しは合意した安全な方法で（メール添付でZIPを送らない）
- [ ] 保管場所、アクセスできる人、保管期限、終了時の削除方法を決めて記録する
- [ ] 個人情報は、必要に応じてマスキングする
- [ ] **外部のLLM APIにデータを送ってよいか** を顧客と合意する（入力が学習に使われない契約・設定か、保存場所・期間はどうか）
- [ ] 送れない場合の代替（閉域環境で動くモデル、ローカルLLM）を検討する

> Algomatic はオープンなLLMを使った自社環境・オンプレミスでのLLM導入支援や、実務で使えるローカルLLMの検証記事を公開しています。
> 「クラウドLLMが使えない＝AI化できない」ではありません。ただし性能・費用が変わるので、その構成のまま評価します。

## 3. 「正解」を定義する

### 3-1. 過去の記録 ≠ 正解

過去に人が作った結果を正解として使うのが基本ですが、そのまま信じてはいけません。

| よくあるズレ | 対処 |
|---|---|
| 担当者ごとの判断の揺れ | どちらを正解とするか責任者に決めてもらう |
| 単純な誤り | 正解データから除外 or 修正 |
| 途中でルールが変わった | 新ルール基準で正解を付け直す |
| 制度・法令が変わった | 期間ごとに正解を分けて扱う |
| 「どちらでも可」 | **許容リスト**（複数を正解として扱う） |

LayerX は、学習・評価データのラベル誤りを **Confident Learning** という手法で見つけてデータ品質を改善する取り組みを公開しています。
手作業でも、「よく似た入力なのに結果が違う」ものを抜き出して現場の担当者に確認してもらうだけで、かなりのノイズが見つかります。

> 📘 **ケーススタディ：仕訳入力の場合**
> 同じ品名なのにAさんは「事務用品費」、Bさんは「消耗品費」で処理していた → 責任者が「消耗品費」に統一。
> 2026年10月にインボイス制度の経過措置が変わったため、9月以前と10月以降で正解の税区分が変わるケースがある → 期間を分けて評価。

### 3-2. 正解確認会と判断ルール集

評価データの中で怪しいもの（揺れ・誤りの疑い）をリストにして、**現場の担当者と一緒に正解を決める会** を開きます。

- 1回60分で50〜100件が目安
- リストには「入力の実物」「過去の結果」「疑問点」を並べておく
- 決まったルールは **「判断ルール集」** として文書化する → **これがそのままAIに渡す知識になる**

```markdown
## 判断ルール集（例：仕訳入力）
- R-001 事務用品通販B社の明細のうち、単価10万円未満の物品は「消耗品費」。10万円以上は経理担当に確認（要確認）
- R-002 会議中の飲食物は「会議費」、懇親会は「交際費」。区別がつかなければ要確認
- R-003 部門は、請求書の「ご注文者」欄の部署名から決める。記載がなければ発注一覧で確認
```

判断ルール集は、AIのためだけのものではありません。**属人化していた判断が文書になること自体が、顧客にとっての成果** です（PoCが不採用になっても残る）。

### 3-3. 誤りの重さを決める

すべての誤りが同じ重さではありません。顧客と **誤りの重さのランク** を合意します。

| ランク | 定義 | 扱い |
|---|---|---|
| **致命的** | お金・法令・社外の相手に直接影響し、後から気付きにくい／取り返しがつかない | **ほぼゼロを目指す。AIが怪しければ必ず人に回す** |
| 重大 | 業務の結果が変わるが、確認工程で見つけられる | 確認で必ず見つかる設計にする |
| 軽微 | 後で直せる、影響が小さい | 定期的に直せればよい |

> 📘 **ケーススタディ：仕訳入力の場合**
> 致命的 ＝ 金額・税区分の誤り、明細の取り漏れ、源泉徴収の漏れ／重大 ＝ 勘定科目の誤り／軽微 ＝ 部門・補助科目の誤り
>
> 他の業務の例は [付録B](./appendix/B-other-use-cases.md) を参照。問い合わせ対応なら「誤った案内を顧客に送る」が致命的です。

## 4. 評価データセットを作る

### 4-1. 何件必要か

正解率を測るときの誤差の目安（正解率90%前後のとき、95%信頼区間）：

| 評価件数 | 誤差の目安 | 使いどころ |
|---|---|---|
| 50件 | ±8ポイント | 開発中の素早い確認 |
| 100件 | ±6ポイント | |
| **300件** | **±3.4ポイント** | **PoCの判断に使う本評価の目安** |
| 1,000件 | ±1.9ポイント | 本番前の最終確認、細かい比較 |

→ 「85%と88%、どちらが良いか」を判断したいなら300件はほしい。
→ ケースの型ごとに精度を見たいなら、**型ごとに最低30〜50件**。

### 4-2. どう選ぶか（層化抽出）

ランダムに選ぶと、件数の多い簡単なケースばかりになり、難しいケースが数件しか入りません。
**ケースの型ごとに件数を決めて選びます**（層化抽出）。PoCの主対象の型は多めに入れます。

> 📘 **ケーススタディ：仕訳入力の場合**
>
> | 型 | 実際の件数比 | 評価データの件数 |
> |---|---|---|
> | 明細多・毎回違う | 20% | 100 |
> | 税率混在・按分 | 8% | 60 |
> | 取引先固定 | 32% | 40 |
> | 毎月定額 | 36% | 30 |
> | 特殊（源泉・前払・外貨） | 4% | 40 |
> | 新規取引先 | — | 30 |
> | **計** | | **300** |

**選ぶときの注意**
- **期間を分ける**：例えば直近3か月を評価用、それ以前を「AIが参照する過去データ」にする。評価対象そのものをAIが参照できると **カンニング** になり、精度が不当に高く出る
- 02で集めた「難しいケース」「新人が間違えるケース」が全部入っているか確認する
- 入力の品質（綺麗なデータ・スキャン・手書きなど）も混ぜる

### 4-3. 評価データの形式

抽出・分類タスクなら、**1行 = 1つの判定単位** のCSVにします。見本は [tools/sample/journal/](./tools/sample/journal/)（仕訳）と [tools/sample/inquiry/](./tools/sample/inquiry/)（問い合わせ分類）。

| 列の種類 | 例 | 説明 |
|---|---|---|
| ID | doc_id, line_no | どの入力のどの部分か |
| 型 | segment | 結果を型ごとに集計するため |
| 正解の項目 | account, department … | AIに当てさせたい項目 |
| 許容する別解 | acceptable_account | どちらでも正解とする値（`;`区切り） |
| メモ | note | 正解確認会での決定事項 |

## 5. タスクの型ごとの評価方法

[00 のタスクの型](./00-concepts.md#3-業務の作業をタスクの型に分ける)によって、評価のしかたが変わります。

| タスクの型 | 評価方法 | 指標の例 |
|---|---|---|
| **抽出・分類・変換** | 正解と項目ごとに突き合わせる | 項目別正解率、完全一致率（→ [tools/evaluate.py](./tools/evaluate.py) で自動化） |
| **検索** | 正しい情報が上位に入っているか | 上位N件に正解が含まれる割合 |
| **チェック（見落としを探す）** | 見つけるべきものを見つけたか／余計な指摘をしていないか | 見落とし率（見つけるべきもののうち見逃した割合）、誤検知率（指摘のうち不要だった割合） |
| **要約・生成** | 正解が1つではないので、**採点基準（ルーブリック）** で採点 | 基準ごとの合格率 |
| **判断・推論** | 専門家の判断との一致 | 一致率。**専門家同士の一致率が上限の目安** |

### 正解が1つではないタスク（要約・生成）の評価

例：問い合わせへの回答メール案。正解の文面は1つではありません。

**1. 採点基準（ルーブリック）を作る**

```
□ 質問されたことに全部答えている
□ 事実が正しい（FAQ・社内資料と矛盾しない）
□ 根拠のない約束をしていない（返金・納期など）
□ 社内の言葉遣いのルールを守っている
□ 個人情報・社外秘を含んでいない
```

**2. 人が採点する**（最初は必須。現場の担当者と一緒に）

**3. 件数が多ければ、LLMに採点させる（LLM-as-a-Judge）**
- 採点用のプロンプトに、ルーブリックを渡して1項目ずつ判定させる
- **必ず人の採点と比べて、どれだけ一致するか確かめてから使う**（一致しないなら採点基準を直す）
- 生成と採点で同じプロンプトを使わない（Algomatic の「生成と評価を分ける」考え方）

**4. 比較評価も有効**：新旧2つの出力を並べて「どちらが良いか」を判定する方が、絶対評価より安定することが多い

## 6. カバレッジと正解率はトレードオフ

AIに「自信がないときは『要確認』にしていい」と許すと、

- AIが回答する量（**カバレッジ**）は **減る**
- 回答した中での正解率は **上がる**

```
       回答した中での正解率
  100% ┤●
       │  ●
   95% ┤     ●        ← この辺りで運用すると「AIが出した答えはほぼ信頼でき、
       │        ●         怪しいものだけ人が見る」状態
   90% ┤            ●
       │                 ●
   85% ┤                       ● ← 全部に答えさせた場合
       └┬────┬────┬────┬────┬──
        50%  60%  70%  80%  90% 100%  カバレッジ
```

**どこで運用するか** が、ビジネス上の判断ポイントです。
「全部答えて85%」より「70%に答えて97%正解、残り30%は人が見る」の方が、**確認の手間が減って業務は楽になる** ことが多いです。
（85%正解でも、どの15%が間違いか分からなければ、結局全部確認することになるため）

> Algomatic の品質保証の記事でも、AIに自信がないときは **「判断保留」** にして人に委ねる仕組みを紹介しています。

### 主な指標（抽出・分類タスクの場合）

| 指標 | 計算式 | 何が分かるか |
|---|---|---|
| 項目別正解率 | 項目が正解の件数 ÷ 全件数 | どの項目が弱いか |
| 完全一致率 | 全項目が正解の件数 ÷ 全件数 | そのまま使える割合 |
| まとまり単位の完全一致率 | 全部正解の書類数 ÷ 書類数 | 「1件まるごと直さなくてよい」割合。**業務効果に近い** |
| カバレッジ | 要確認にしなかった件数 ÷ 全件数 | AIに任せられる量 |
| 回答した中での完全一致率 | 回答した中で完全一致の件数 ÷ 回答した件数 | AIが自信を持って出した答えの信頼度 |
| **回答した中での致命的誤り率** | 回答した中で致命的な誤りの件数 ÷ 回答した件数 | **これが高いと使えない** |
| 処理時間・コスト | 1件あたりの秒数・費用 | 業務に乗るか、元が取れるか |

## 7. 平均だけ見ない（切り口を変えて見る）

LayerX は AI-OCR の精度を **様々な観点でモニタリング** し、ボトルネックを可視化して「勘ではなく事実に基づいて」改善するとしています。最低限、以下の切り口で集計します。

- ケースの型別
- 項目別
- 入力の品質別（綺麗なデータ / スキャン / 手書き）
- 入力の長さ・複雑さ別
- 過去データの有無別（既知のケース / 初めてのケース）

## 8. 合格基準を決める（PoC開始前に！）

PoC終了時に「本番化に進むか」を判断する基準を、**PoCを始める前に** 顧客と合意します。後から決めると、結果に合わせて基準を動かしたくなり、揉めます。

基準は「必須（満たさなければ本番化しない）」と「目標（満たせば効果が大きい）」に分けます。**致命的誤り率は必ず必須に入れます。**

> 📘 **ケーススタディ：仕訳入力の場合**
> ```markdown
> ## PoC合格基準（2026-10-28 合意）
> 評価データ：300件（直近3か月の請求書、型別に層化抽出）
> ### 必須
> 1. 致命的誤り率（AIが回答した行のうち）：1%以下
> 2. カバレッジ：60%以上
> 3. AIが回答した行の完全一致率：95%以上
> ### 目標
> 4. 請求書単位の完全一致率：70%以上
> 5. 明細が多い型の完全一致率：90%以上
> 6. 処理時間：1件あたり60秒以内
> ```

## 10. 注意点

- **カンニングに注意。** 評価対象を、AIが参照する過去データに含めない。期間で分けるのが一番安全。
- **正解を勝手に決めない。** 「たぶんこっちが正しい」で直さず、必ず現場の担当者に確認する。
- **評価データは固定する。** 途中で入れ替えると前回と比較できない。追加するならバージョンを分ける（v1, v2）。
- **評価データに過剰適合しない。** 評価データの誤りだけを狙って直していると、本番で同じ精度が出ない。開発用と評価用を分けるか、定期的に新しいデータで確認する。
- **制度変更・ルール変更の境目に注意。** 変更をまたぐデータでは、同じ入力でも正解が変わりうる。
