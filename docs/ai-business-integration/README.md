# 業務にAIを組み込む 新人ハンドブック

> **このハンドブックのゴール**
> 顧客から「この業務をAIで効率化したい」と相談されたとき、
> 新人でも **何を・どの順番で・どう進め、どこに気を付ければよいか** が分かり、翌日から手を動かせる状態になること。

対象は特定の業務ではありません。請求書処理、問い合わせ対応、契約書チェック、営業メール作成など、**「人が書類やデータを読んで、判断して、何かを入力・作成している業務」** なら同じ進め方が使えます。

説明を具体的にするため、全章を通じて **「経理の仕訳入力業務」** を題材（ケーススタディ）に使います。
これはあくまで例です。題材の業務知識を覚えることが目的ではなく、**どの業務に入っても使える「型」を身につけること** が目的です。

内容は LayerX と Algomatic のエンジニアブログで公開されている、LLM・AIエージェントを実業務に組み込む際の知見を土台にしています（[参考資料](./references.md)）。

---

## 想定するシチュエーション

- 顧客（事業会社）から「○○業務をAIで効率化したい」と相談を受けた
- ベンダーである私たちが、**業務調査 → 検証（PoC）→ 本番実装 → 運用定着** までを担当する
- あなたは新人メンバーとして、PM・エンジニアと一緒にプロジェクトに入る

## 全体像

### 7つのフェーズ

```
 ┌─────────────┐   ┌──────────────────┐   ┌──────────────────┐
 │①キックオフ   │→ │②現状業務の把握      │→ │③データ・評価設計   │
 │目的とKPI合意 │   │どこにAIを使うべきか │   │何をもって正解か    │
 └─────────────┘   └──────────────────┘   └────────┬─────────┘
                                                    ↓
 ┌─────────────┐   ┌─────────────┐        ┌──────────────────┐
 │⑥本番実装     │← │⑤Go/No-Go    │←────── │④PoC（検証）       │
 │業務に組み込む │   │やる範囲を決定 │        │小さく作って測る     │
 └──────┬──────┘   └─────────────┘        └──────────────────┘
        ↓
 ┌──────────────────────────────────────────┐
 │⑦運用・継続改善  人の修正を改善に戻し、使うほど賢く        │
 └──────────────────────────────────────────┘
```

### 全フェーズを貫く5つの原則

1. **AIを入れること自体を目的にしない。** 目的は顧客の業務の成果（時間、品質、スピード、属人化の解消）。AIは手段の1つで、ルールや既製サービスの方が良いこともある。
2. **AIは100%正解しない。だから「間違えても困らない業務の流れ」ごと設計する。**
   精度を上げる努力と同じくらい、「間違いにすぐ気づける・すぐ直せる」仕組みが大事。（LayerX「LLMの不確実性との付き合い方」）
3. **評価できないものは改善できない。作る前に「何をもって正解か」を決める。**
   デモが動いた、触ってみて良さそう、では判断しない。決めたデータと指標で数字を出す。（LayerX「評価駆動開発」、Algomatic「LLM品質保証テクニック」）
4. **業務の専門家（現場の担当者）と一緒に作る。** 正解を知っているのは現場の人。ベンダーだけでは正解が決められない。
5. **作って終わりにしない。** 人の修正が次の改善につながる仕組みにする。（LayerX「使えば使うほど賢くなるAI機能」）

### スケジュール例（PoCまで約3か月）

| 週 | フェーズ | 主な成果物 | 顧客に会う場 |
|---|---|---|---|
| 1 | ①キックオフ | プロジェクト計画書、KPI合意メモ | キックオフ会議 |
| 2–4 | ②現状業務把握 | 業務入門メモ、業務フロー図、業務棚卸しシート、時間計測結果 | ヒアリング×3〜5回、業務観察×2回 |
| 3–5 | ③データ・評価設計 | データ依頼書、評価データセット、評価指標・合格基準の合意書 | 正解確認会×2回 |
| 6–10 | ④PoC | ベースライン結果、PoCシステム、週次の評価結果、エラー分析 | 週次定例 |
| 11–12 | ⑤判断 | PoC報告書、費用対効果試算、本番化の提案書 | 報告会 |
| 13〜 | ⑥本番実装 | 要件定義書、本番システム、運用マニュアル | 隔週定例、受入テスト |
| 本番後 | ⑦運用 | 精度ダッシュボード、月次改善レポート | 月次定例 |

> ②と③は重なって進みます。業務を見ながら「どのデータを貰うか」を決めていくためです。規模・体制で大きく変わるので、あくまで目安です。

### 役割分担（RACI）

R=実行する人、A=最終責任者、C=相談される人、I=報告を受ける人

| 作業 | 顧客 部門責任者 | 顧客 現場担当者 | 顧客 情シス | 当社 PM | 当社 エンジニア | **あなた（新人）** |
|---|---|---|---|---|---|---|
| KPI・目的の合意 | A | C | I | R | C | 議事録 |
| ヒアリング・業務観察 | I | C | C | A | C | **R（記録・図にする）** |
| データ提供 | A | R | R | C | C | **依頼書作成・受領管理** |
| 正解の定義・確認 | A | R | – | C | C | **確認リスト作成** |
| PoC開発・評価 | I | C | – | A | R | **評価実行・エラー分析** |
| 報告・判断 | A | C | C | R | C | **資料の数字づくり** |
| 本番実装 | A | C | R | A | R | テスト・マニュアル |
| 運用改善 | A | R | C | R | R | **月次レポート** |

> 新人の担当になりやすいのは「記録する」「数える」「並べて比べる」仕事です。
> 地味に見えますが、AI案件の品質はほぼここで決まります。各章に「新人のタスク」欄を設けています。

## このハンドブックの読み方

各章は次の順で書いています。

1. **目的・やること（どの業務でも共通の進め方）**
2. **📘 ケーススタディ：仕訳入力の場合** … 題材に当てはめるとどうなるか（囲みで表示）
3. **新人のタスク → 注意点 → 完了チェック**

ケーススタディの業務知識が分からなくても、1と3は読めるように書いています。
自分の担当業務に置き換えるときは、次の対応表を参考にしてください。

| ハンドブックの一般用語 | 仕訳入力の場合 | 問い合わせ対応の場合 | 契約書チェックの場合 |
|---|---|---|---|
| 入力（AIが読むもの） | 請求書・領収書 | 問い合わせメール | 契約書ドラフト |
| 出力（AIが作るもの） | 仕訳（科目・部門・税区分） | 分類・担当振り分け・回答案 | 指摘事項・修正案 |
| 業務の専門家 | 経理担当者 | サポート担当者 | 法務担当者 |
| 判断のよりどころ | 経理規程・過去の仕訳 | FAQ・過去の回答 | 契約審査基準・過去の審査記録 |
| 致命的な誤り | 税額・金額の誤り | 誤った案内で顧客に損害 | 重大なリスク条項の見落とし |
| 後工程 | 承認・支払・月次決算 | 顧客への返信 | 相手方との交渉 |
