# 06 本番実装：業務の流れごと作る

[← 目次へ](./README.md) ｜ 前：[05 Go/No-Go 判断と報告](./05-decision.md)

> **この章のゴール**
> - 「AIが間違えても困らない」業務の流れと画面を設計できる
> - 本番で必要になる仕組み（ログ、回帰テスト、監査証跡、障害時の代替）を漏れなく挙げられる
> - 安全にリリースする手順（並行稼働 → 段階拡大）を説明できる

---

## 1. PoCと本番の違い

| 観点 | PoC | 本番 |
|---|---|---|
| 目的 | 判断材料を集める | 毎日の業務を回す |
| 入力 | 選んだ評価データ | 何が来るか分からない（新しい取引先、変な書式） |
| 失敗したとき | 結果が悪いだけ | **月次決算・支払・納税に影響** |
| 使う人 | 開発メンバー | 経理担当者（AIに詳しくない） |
| 期間 | 数週間 | 何年も（制度・マスタ・担当者が変わる） |

→ 本番では、**AIの精度そのものより「業務の流れ」と「運用の仕組み」の作り込みが大半** を占めます。

## 2. To-Be 業務の流れを設計する

### 原則：AIは下書き、確定するのは人

```
 Before（今）                            After（To-Be）
 ─────────────                          ──────────────
 証憑を読む                              証憑が届く → AIが自動で読み取り・仕訳案を作成
 過去の仕訳を調べる                            ↓
 科目・部門・税区分を判断                  ┌────────────┬─────────────┐
 会計ソフトに入力                        │ 自動OK（約70%）│ 要確認（約30%）  │
 上長が承認                              │ 一覧でざっと確認 │ 根拠を見て修正   │
                                        │ → 一括承認     │ → 承認          │
                                        └────────────┴─────────────┘
                                               ↓
                                        会計ソフトへ連携（CSV/API）
                                               ↓
                                        人の修正内容を記録 → 改善に使う（→ 07）
```

### LayerX の考え方：間違いから回復しやすい流れにする

LayerX の「LLMの不確実性との付き合い方」では、

- LLMの誤りが業務に与える悪影響は **体験設計次第** である
- だから精度の測定に加えて、**後工程（下流のプロセス）への影響** に注意する
- **LLMの間違いからリカバリーしやすいワークフロー** にする（例：網羅的に出力し、編集可能な形にする）

と整理しています。仕訳に当てはめると：

| 設計の工夫 | なぜ |
|---|---|
| AIの出力は「案」として編集可能な状態で出す | 間違っていてもその場で直せる |
| 要確認の行を目立たせ、自動OKの行と分ける | 人の注意を必要なところに集中させる |
| 根拠（参照した過去仕訳・ルール）を横に表示 | 確認が速くなる、誤りに気付きやすい |
| 証憑の画像と仕訳を並べて表示し、該当箇所をハイライト | 読み取りミスに気付ける |
| 承認前に必ず人の目を通す | 誤りが会計ソフト・支払に流れない |
| 会計ソフトへの連携後も取り消し・修正できる | 月次チェックで見つかっても直せる |

### 責任分界を明文化する

| 項目 | 責任者 |
|---|---|
| 仕訳案の作成 | システム（AI） |
| 仕訳の確定・承認 | 顧客の経理担当者・承認者 |
| 判断ルール・マスタの維持 | 顧客の経理部（当社は支援） |
| システムの稼働・精度の監視 | 当社（保守契約の範囲） |

## 3. 確認画面の設計

経理担当者が毎日何百件も見る画面です。**クリック数と目の移動を減らす** ことが、そのまま効果になります。

### 必須の要素

```
┌──────────────────────────────┬──────────────────────────────────┐
│ 証憑の画像（PDF）               │ 仕訳案                              │
│                              │ 取引先: 事務用品通販B社  T1234...     │
│  ┌────────────────────┐       │ ─────────────────────────────── │
│  │ 1 トナー   24,000   │ ←──── │ 1 消耗品費 ▼ 営業部 ▼ 10% ▼ 24,000  ✓ │
│  │ 2 チェア  128,000   │ ←──── │ 2 工具器具備品 ▼ 物流部 ▼ 10% ▼ 128,000 ⚠│
│  │ ...                │       │   ⚠ 10万円以上の物品です（R-001）       │
│  └────────────────────┘       │   根拠: 過去仕訳 2026-03 チェア→備品     │
│                              │ ─────────────────────────────── │
│                              │ 合計 152,000 ＝ 請求書合計 152,000 ✓  │
│                              │ [承認] [差し戻し] [次の要確認へ]        │
└──────────────────────────────┴──────────────────────────────────┘
```

- **修正はドロップダウン（候補から選ぶ）** にする。自由入力だとマスタにない値やゆれが混入し、修正データも学習に使いにくい
  - LayerX は、ドロップダウンで候補を表示してユーザーが負担なく修正できるようにし、その **構造化された修正データ** を集めて定期的にモデルを更新する仕組みを紹介しています（→ [07](./07-operation.md)）
- 候補の並び順は「AIの推奨 → 過去にこの取引先で使った科目 → その他」
- キーボードだけで操作できる（Tabで移動、Enterで承認）
- 一覧画面では、要確認の件数と理由でフィルタできる

### 画面設計で必ず経理担当者に見てもらう

紙芝居（画面のモックアップ）の段階で、実務担当者に **実際の請求書を使って操作してもらいます**。
「この順番で見ない」「ここに部門コードも出してほしい」などの指摘は、作る前に貰うほど安く済みます。

## 4. システム構成と連携

```
 証憑の入口                   AI処理                         確認・確定              会計
 ─────────                  ────────                       ─────────            ────────
 メール受信 ─┐            ┌→ ①読み取り                     確認画面               会計ソフト
 共有フォルダ ─┼→ 取込キュー ─┼→ ②参考情報の検索  → 仕訳案DB →（人が確認・修正）→ 承認 → CSV出力/API
 既存システム ─┘            └→ ③判断 → ④チェック → ⑤振り分け
                                    ↑                              │
                               マスタ同期 ←── 会計ソフトのマスタ          │
                                    ↑                              ↓
                               判断ルール集                    修正ログ → 改善（07）
```

### 決めること（要件定義のチェックリスト）

**連携**
- [ ] 証憑の取り込み方法（メール転送、フォルダ監視、既存システムAPI）
- [ ] 会計ソフトへの連携方法（CSV取込の仕様、API）と、取込エラー時の扱い
- [ ] マスタ（科目・部門・税区分・取引先）の同期方法と頻度
- [ ] 二重計上の防止（同じ請求書が2回届いた場合）

**品質・運用（LLMOps）**
- [ ] すべての処理の **ログ（トレース）** を残す：入力、使ったプロンプトのバージョン、モデル、出力、処理時間、費用
- [ ] **プロンプトのバージョン管理**：プロンプトを変えたら、いつ・誰が・何を変えたか残る
- [ ] **回帰テスト**：プロンプト・モデル・ルールを変えたら、評価データセットで自動採点し、基準を下回ったらリリースしない
- [ ] モデルの提供元が古いモデルを廃止したときの移行手順（新しいモデルで評価し直す）

> LayerX は Langfuse を LLMOps の基盤として採用し、プロンプトをプロダクトのコードとは独立して管理しつつ、
> データセットを使った自動的な回帰テストや、独自の評価基準での採点を行っていると紹介しています。

**セキュリティ・統制**
- [ ] データの保存場所と暗号化、アクセス権限（誰がどの会社・部門の証憑を見られるか）
- [ ] 外部LLM APIの利用条件（入力データが学習に使われない契約・設定か、保存期間、リージョン）
- [ ] 個人情報のマスキング
- [ ] 証憑内の文言を「指示」として扱わない対策（プロンプトインジェクション対策）とそのテスト
- [ ] **監査証跡**：どの仕訳を、AIが提案し、誰が修正・承認したか、いつ会計ソフトに連携したか
- [ ] 電子帳簿保存法の要件（証憑の保存・検索・改ざん防止）を、既存の保存の仕組みと合わせて満たすか

**障害・例外**
- [ ] AIが止まったとき（API障害、レート制限）でも、**従来どおり手入力で業務が回る** こと
- [ ] 処理が遅れたときの通知
- [ ] 費用の上限（異常な大量処理で請求が膨らまないように）

## 5. テスト

| テスト | 内容 | 誰が |
|---|---|---|
| 単体・結合テスト | 部品ごと・つないだときに正しく動くか | 当社 |
| 評価データでの回帰テスト | PoCと同等以上の精度が出るか | 当社 |
| 頑健性テスト | [04 の動作検証](./04-poc.md#8-step-6速度コスト揺れ頑健性を測る) をテストとして自動化 | 当社 |
| 受入テスト | 実際の業務シナリオで、経理担当者が操作して確認 | 顧客（当社が支援） |
| 連携テスト | 会計ソフトに取り込んで、試算表の数字が合うか | 顧客＋当社 |

## 6. リリースの進め方（いきなり全部切り替えない）

```
 Phase 1 並行稼働（1か月）
   AIは仕訳案を作るが、担当者は従来どおり手入力。後でAI案と人の入力を比べて、本番データでの精度を測る
     ↓ 本番データで合格基準を満たすことを確認
 Phase 2 限定開始（1か月）
   対象を絞って（例：明細多の請求書、担当者1名）、AI案を確認・修正する運用に切り替える
     ↓ 問題がなければ
 Phase 3 拡大
   対象の型・担当者を広げる
     ↓
 Phase 4 自動化レベルを上げる
   実績が溜まった型（例：3か月連続で誤りゼロの取引先）は確認を簡略化する
```

**ポイント**
- **並行稼働（シャドー運用）で、本番データでの精度を必ず確かめる。** 評価データと本番では分布が違う
- **月次決算の締め直前・決算月にはリリースしない。** 月初の締めが終わった直後が安全
- 自動化レベルを上げる（確認を減らす）のは、**実績データで根拠を示してから**。LayerX も業務の自動化を段階的なレベルとして捉えています

## 9. 注意点

- **AIの精度より、業務の流れの方が効果を左右する。** 精度が高くても、確認画面が使いにくければ時間は減らない。
- **自動で通す範囲は、本番データの実績で決める。** PoCの数字だけで「自動OK」を広げない。
- **「人が見ているから大丈夫」に頼りすぎない。** AIの案が大体正しいと、人は確認が雑になる（自動化バイアス）。要確認の行を絞り、そこは確実に見てもらう設計にする。定期的に自動OKの行を抜き取り検査する。
- **ログが残っていないと、後から何も分からない。** 「なぜこの仕訳になったか」を後で追えることが、改善にも監査にも必須。
