# 01 キックオフ：目的とゴールを合意する

[← 目次へ](./README.md) ｜ 前：[00 経理・仕訳の基礎](./00-basics.md)

> **この章のゴール**
> - 「AIで仕訳を効率化したい」というふわっとした依頼を、**数字で測れるゴール** に変換できる
> - キックオフで何を聞き、何を決め、何を持ち帰るかが分かる

---

## 1. なぜここが一番大事か

AI案件の失敗で一番多いのは「技術的にできなかった」ではなく、**「何ができたら成功か決めていなかった」** です。

- 顧客は「9割自動化」を想像していたのに、こちらは「下書き提案で入力時間半減」を目指していた
- PoCで精度85%が出たが、それが良いのか悪いのか誰も判断できない
- 「AIで何かやった」実績だけ残り、本番化されない

→ キックオフでは **課題・目的・測り方・判断基準・体制** を言語化して、文書で合意します。

---

## 2. 事前準備（キックオフの1週間前まで）

| やること | 担当 | 新人の関わり方 |
|---|---|---|
| 顧客企業の基本情報を調べる（業種、規模、拠点、上場有無、決算期） | PM | **調べて1枚にまとめる** |
| 業種特有の経理論点を調べる（例：卸売なら仕入・軽減税率が多い） | PM | **[00 基礎](./00-basics.md) の型のどれが多そうか予想する** |
| 事前質問票を送る（下記） | PM | **質問票のドラフトを作る** |
| アジェンダと資料を作る | PM | 資料の体裁・図を作る |

### 事前質問票（顧客に先に送って書いてもらう）

```
1. 月あたりの仕訳件数（おおよそで可）と、その内訳（請求書・経費精算・銀行明細など）
2. 仕訳入力に関わっている人数と、1か月あたりの作業時間（おおよそで可）
3. 使っている会計ソフト・経費精算システム・請求書受取システムの名称
4. 証憑の受け取り方法（紙・PDFメール・システム経由）とそれぞれの割合
5. 税込経理／税抜経理のどちらか
6. 月次決算の締め日数（例：月初から○営業日）
7. 現在いちばん困っていること（自由記述）
8. 今回の取り組みで「こうなったら成功」と思う状態（自由記述）
```

## 3. キックオフ当日：聞くこと・決めること

### 3-1. 課題の深掘り（「なぜ？」を3回）

顧客の最初の言葉はたいてい **手段** です。**目的** まで掘り下げます。

```
顧客：「AIで仕訳を自動化したい」
  ↓ なぜ自動化したいのですか？
顧客：「入力に時間がかかりすぎている」
  ↓ 時間がかかると、何が困りますか？
顧客：「月初の締めが8営業日かかって、経営会議に数字が間に合わない」
  ↓ 締めが早くなると、何が嬉しいですか？
顧客：「経営判断が早くなる。あと、担当者の残業を減らして、1人辞めても回る体制にしたい」
```

→ この案件の本当の目的は **「締め日数の短縮」と「属人化の解消」**。
「入力時間の削減」はそのための手段の1つにすぎない、と分かります。
（入力ではなく、**確認・差し戻し** に時間がかかっているなら、打ち手が変わる）

### 3-2. KPI（成功の測り方）を決める

目的に対応する指標を、**今の値（ベースライン）と目標値** のセットで決めます。

| 目的 | KPI | 今の値（例） | 目標（例） | 測り方 |
|---|---|---|---|---|
| 締め日数の短縮 | 月次決算の締め日数 | 8営業日 | 5営業日 | 経理部の締めスケジュール実績 |
| 作業時間の削減 | 仕訳1件あたりの処理時間 | 約3分 | 1分以下 | 業務観察で計測（→[02](./02-as-is.md)） |
| 作業時間の削減 | 仕訳関連の月間作業時間 | 約200時間 | 80時間 | 担当者の作業ログ |
| 品質の維持・向上 | 月次チェックでの差し戻し件数 | 月約120件 | 現状以下 | 差し戻しの記録 |
| 属人化の解消 | 新任者が独力で入力できるまでの期間 | 3か月 | 1か月 | 人事・経理部長へのヒアリング |

**KPIを決めるときのコツ**

- **今の値が分からないKPIは、まず測ることから** 始める（②現状業務把握のタスクになる）
- 目標値はキックオフで無理に決めなくてよい。「PoCの結果を見て決める」と合意しておけばOK
- **「精度○%」だけをKPIにしない**。精度は手段の指標。顧客にとっての価値（時間・締め日数・品質）と必ずセットにする
- 「品質を下げない」を必ず入れる。速くなっても誤りが増えたら意味がない

### 3-3. スコープ（今回やる範囲）を決める

最初から全部はやりません。キックオフでは **候補** を挙げて、②で決めます。

| 候補 | 件数/月 | 難しさ | 今回の扱い（キックオフ時点） |
|---|---|---|---|
| 請求書受取の仕訳 | 2,500 | 中〜高 | **最有力候補** |
| 経費精算の仕訳 | 1,000 | 中 | 候補（既存の経費精算システムの機能で足りるか確認） |
| 銀行・カード明細の仕訳 | 500 | 低〜中 | 会計ソフトの自動仕訳ルールで足りる可能性 |
| 売上の仕訳 | — | — | **対象外**（販売管理システムから自動連携済み） |

### 3-4. 体制と役割を決める

**必ず顧客側に出してもらう人**

| 役割 | なぜ必要か |
|---|---|
| 経理部長（意思決定者） | 「この精度で本番化するか」を決める人。報告会に必ず出てもらう |
| **経理の実務担当者（1〜2名）** | **正解を判断できる唯一の人**。ヒアリング、正解確認、テストに週2〜3時間もらう |
| 情報システム担当 | データの取り出し、セキュリティ審査、本番のシステム連携 |

> 実務担当者の時間が取れない案件は、ほぼ確実に失敗します。
> 「週○時間、この方の時間をください」と **具体的に** お願いしてください。

### 3-5. 制約・前提を確認する

| 確認事項 | なぜ聞くか |
|---|---|
| データを社外（当社・クラウドLLM）に出してよいか、条件は | 使える技術が変わる。ダメなら閉域環境・ローカルLLMの検討が必要 |
| 個人情報（従業員の氏名・口座、個人取引先）の扱い | マスキングの要否 |
| 予算・納期の目安、決裁の時期 | PoCの規模を決める |
| 会計ソフトの変更予定 | 連携先が変わるならPoCの設計が変わる |
| 監査法人・顧問税理士への説明の要否 | 本番化時に内部統制の説明が必要になる |
| 繁忙期（決算月、年末調整など） | ヒアリングやテストを入れてはいけない時期 |

## 4. キックオフ後に作るもの（成果物）

### プロジェクト計画書（1〜3枚でよい）

```markdown
# 仕訳入力業務効率化 PoC 計画書（株式会社みどり物産 様）

## 1. 背景と目的
- 月次決算に8営業日かかり、経営会議への報告が遅れている
- 仕訳入力・確認に月約200時間、担当者3名に依存している
- 目的：締め日数の短縮と、属人化の解消

## 2. KPI（暫定、②の調査後に確定）
| KPI | 現状 | 目標 |
| 仕訳1件あたりの処理時間 | 約3分（要計測） | PoC結果を見て決定 |
| 月次差し戻し件数 | 約120件（要計測） | 現状以下 |

## 3. スコープ
- 対象：請求書受取の仕訳（月約2,500件）
- 対象外：売上仕訳、給与仕訳

## 4. 進め方とスケジュール
- 第2〜4週：業務調査 / 第3〜5週：データ準備・評価設計 / 第6〜10週：PoC / 第11〜12週：報告

## 5. 体制
- 御社：経理部長 ○○様、経理担当 ○○様（週3時間）、情シス ○○様
- 当社：PM ○○、エンジニア ○○、○○

## 6. 前提・制約
- 証憑・仕訳データは匿名化のうえ当社の検証環境で扱う（データ取扱いの覚書を締結）
- 決算月（3月）は作業を入れない

## 7. PoC終了時の判断基準（暫定）
- 評価データで「人が修正不要な仕訳の割合」が○%以上 かつ 致命的な誤り（※）が○%以下
  ※ 税区分の誤り、金額の誤り、源泉徴収の漏れ
```

### 議事録（新人の担当になりやすい）

**良い議事録の条件**：「決まったこと」「宿題（誰が・いつまでに）」「保留事項」が一目で分かること。発言録ではありません。

```markdown
# キックオフ議事録 2026-10-07
## 決定事項
- PoCの対象は請求書受取の仕訳とする
- 経理担当 A様に週3時間ご協力いただく
## 宿題
| # | 内容 | 担当 | 期限 |
| 1 | 過去12か月の仕訳データ（CSV）の提供 | 情シス B様 | 10/14 |
| 2 | データ取扱い覚書のドラフト送付 | 当社 PM | 10/9 |
| 3 | 業務観察の日程調整 | 当社 新人 | 10/9 |
## 保留・要確認
- クラウドLLMの利用可否 → 情シス部長に確認（10/14の定例で回答）
```

## 6. 注意点

- **「100%自動化」「完全に人が要らなくなる」と言わない。** LayerX も業務の自動化を段階（レベル）で捉えています。まずは「AIが下書き、人が確認」から始め、精度と信頼が溜まった型から確認を減らしていく、と説明します。
- **「精度」の話だけで合意しない。** 「精度90%」は、残り10%を見つけて直す作業が残るという意味です。その10%を探す手間が大きければ、効率化になりません（→ [04 PoC](./04-poc.md)、[06 本番実装](./06-implementation.md)）。
- **費用対効果の軸を早めに出す。** 「月○時間削減 × 時間単価」と「開発費・利用料」を比べる、という考え方を初回から共有しておくと、後の判断がスムーズです（→ [05](./05-decision.md)）。
- **新人がその場で答えられない質問は、無理に答えず持ち帰る。** 「確認して○日までにご回答します」で十分です。
