# 仕訳入力業務の効率化プロジェクト 新人ハンドブック

> **このハンドブックのゴール**
> 経理の知識もAI案件の経験もない新人が、これを読んだ翌日から
> 「何を・誰に・どう聞き／作り／報告すればよいか」が分かり、手を動かせる状態になること。

想定するシチュエーション：

- 顧客（事業会社の経理部門）から「仕訳入力の手間を減らしたい」と相談を受けた
- ベンダーである私たちが、**業務調査 → 検証（PoC）→ 本番実装 → 運用定着** までを担当する
- あなたは新人メンバーとして、PM・エンジニアと一緒にプロジェクトに入る

内容は LayerX（バクラク / Ai Workforce）と Algomatic のエンジニアブログで公開されている考え方を土台にしています（[参考資料](./references.md)）。

## 全体像

### 7つのフェーズ

```
 ┌─────────────┐   ┌─────────────┐   ┌──────────────────┐
 │①キックオフ   │→ │②現状業務把握 │→ │③データ・評価設計   │
 │目的とKPI合意 │   │どこに時間が？ │   │何をもって正解か    │
 └─────────────┘   └─────────────┘   └────────┬─────────┘
                                               ↓
 ┌─────────────┐   ┌─────────────┐   ┌──────────────────┐
 │⑥本番実装     │← │⑤Go/No-Go    │← │④PoC（検証）       │
 │業務に組み込む │   │やる範囲を決定 │   │小さく作って測る     │
 └──────┬──────┘   └─────────────┘   └──────────────────┘
        ↓
 ┌─────────────────────────────────────┐
 │⑦運用・継続改善  人の修正を学習に戻し、使うほど賢く │
 └─────────────────────────────────────┘
```

### 全フェーズを貫く3つの原則

1. **AIは100%正解しない。だから「間違えても困らない業務の流れ」ごと設計する**
   精度を上げる努力と同じくらい、「間違いにすぐ気づける・すぐ直せる」仕組みが大事。
   （LayerX「LLMの不確実性との付き合い方」）
2. **評価できないものは改善できない。作る前に「何をもって正解か」を決める**
   デモが動いた、触ってみて良さそう、では判断しない。決めたデータと指標で数字を出す。
   （LayerX「評価駆動開発」、Algomatic「LLM品質保証テクニック」）
3. **作って終わりにしない。人の修正が自動で次の改善につながる仕組みにする**
   （LayerX「使えば使うほど賢くなるAI機能」）

### スケジュール例（標準的な中堅企業、PoCまで約3か月）

| 週 | フェーズ | 主な成果物 | 顧客に会う場 |
|---|---|---|---|
| 1 | ①キックオフ | プロジェクト計画書、KPI合意メモ | キックオフ会議 |
| 2–4 | ②現状業務把握 | 業務フロー図、業務棚卸しシート、時間計測結果 | ヒアリング×3〜5回、業務観察×2回 |
| 3–5 | ③データ・評価設計 | データ依頼書、評価データセット、評価指標・合格基準の合意書 | 正解確認会×2回 |
| 6–10 | ④PoC | ベースライン結果、PoCシステム、週次の評価結果、エラー分析 | 週次定例 |
| 11–12 | ⑤判断 | PoC報告書、費用対効果試算、本番化の提案書 | 報告会 |
| 13〜 | ⑥本番実装 | 要件定義書、本番システム、運用マニュアル | 隔週定例、受入テスト |
| 本番後 | ⑦運用 | 精度ダッシュボード、月次改善レポート | 月次定例 |

> ②と③は重なって進みます。業務を見ながら「どのデータを貰うか」を決めていくためです。
> 規模・体制で大きく変わるので、あくまで目安です。

### 役割分担（RACI）

R=実行する人、A=最終責任者、C=相談される人、I=報告を受ける人

| 作業 | 顧客 経理部長 | 顧客 経理担当 | 顧客 情シス | 当社 PM | 当社 エンジニア | **あなた（新人）** |
|---|---|---|---|---|---|---|
| KPI・目的の合意 | A | C | I | R | C | 議事録 |
| ヒアリング・業務観察 | I | C | C | A | C | **R（記録・図にする）** |
| データ提供 | A | R | R | C | C | **依頼書作成・受領管理** |
| 正解の定義・確認 | A | R | – | C | C | **確認リスト作成** |
| PoC開発・評価 | I | C | – | A | R | **評価実行・エラー分析** |
| 報告・判断 | A | C | C | R | C | **資料の数字づくり** |
| 本番実装 | A | C | R | A | R | テスト・マニュアル |
| 運用改善 | A | R | C | R | R | **月次レポート** |

> 新人の担当になりやすいのは「記録する」「数える」「並べて比べる」仕事です。
> 地味に見えますが、この案件の品質はほぼここで決まります。各章に「新人のタスク」欄を設けています。

## このハンドブックの使い方

- 各章は **目的 → やること（手順）→ 新人のタスク → 成果物 → 注意点 → 完了チェック** の順で書いています。
- 架空の顧客 **「株式会社みどり物産」**（後述）を全章で例に使い、「実際にはこうなる」が分かるようにしています。
- 分からない用語は [00 経理・仕訳の基礎](./00-basics.md) の用語集を見てください。

### 架空の案件：株式会社みどり物産

| 項目 | 内容 |
|---|---|
| 業種・規模 | 食品卸売、従業員300名、拠点5か所 |
| 経理体制 | 経理部長1名、担当者4名（うち仕訳入力の中心は3名） |
| 月の仕訳件数 | 約4,000件（請求書受取 2,500 / 経費精算 1,000 / 銀行・カード明細 500） |
| 会計システム | 会計ソフト（CSV取込に対応） |
| 顧客の困りごと | 「月初の締め作業が8営業日かかる。仕訳入力と確認で残業が月平均40時間。担当者が1人辞めると回らない」 |
| 依頼内容 | 「AIを使って仕訳入力を効率化したい。まず効果があるか検証してほしい」 |

## 注意

税制（インボイス制度の経過措置、少額減価償却資産の特例など）は毎年のように変わります。
本ハンドブックは **2026年10月時点** の情報で書いています。
実際の案件では、必ず顧客の経理規程・顧問税理士の見解・最新の法令を確認してください。
