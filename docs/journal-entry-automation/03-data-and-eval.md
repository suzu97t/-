# 03 データと評価の設計

[← 目次へ](./README.md) ｜ 前：[02 現状業務の把握](./02-as-is.md)

> **この章のゴール**
> - 顧客に何のデータを、どの形式で、どう安全に貰うかを依頼できる
> - 「何をもって正解とするか」を顧客と合意できる
> - 評価データセットを作り、指標と合格基準を決められる
>
> **この章がプロジェクトの成否を分けます。** ここを雑にすると、PoCの結果が「良いのか悪いのか誰にも分からない」状態になります。

---

## 1. なぜ「評価」から先に作るのか

LLMを使ったシステムには、普通のプログラムと違う性質があります。

- **同じ入力でも出力が揺れる**（毎回少しずつ違う答えを返すことがある）
- **プロンプトを1か所直すと、思わぬところが壊れる**（影響範囲が読めない）
- **100%は正解しない**

LayerX はこれを踏まえ、**評価駆動開発（Eval-driven development）** を掲げています。
「評価データと採点方法を先に用意し、変更のたびに全件で採点して、良くなったか悪くなったかを数字で確かめる」やり方です。
Algomatic も、LLMの品質保証として **誤りのパターンを言語化し、人の検証で継続的に改善する** ことを重視しています。

```
×  作る → 触ってみる → なんとなく良さそう → 顧客に見せる → 「ここ違うね」 → 直す → 別のところが壊れる …
○  評価データを作る → 作る → 全件採点 → 誤りを分析 → 直す → 全件採点（悪化していないか確認）→ …
```

## 2. データを貰う

### 2-1. 依頼するデータ

[templates/data-request.md](./templates/data-request.md) に依頼書のひな形があります。

| データ | 用途 | 量の目安 | 形式 |
|---|---|---|---|
| **過去の仕訳データ** | 正解ラベル、過去仕訳の参照、集計 | 12か月分 | 会計ソフトから出力したCSV |
| **その仕訳の元になった証憑** | AIの入力 | 評価用に300〜500件分 | PDF・画像 |
| 仕訳と証憑の対応表 | どの証憑がどの仕訳か | 上記と同じ | 証憑番号や伝票番号での対応 |
| 勘定科目マスタ | AIが選べる選択肢 | 全件 | CSV |
| 補助科目・部門・税区分マスタ | 同上 | 全件 | CSV |
| 取引先マスタ | 取引先の名寄せ、個人/法人、登録番号 | 全件 | CSV |
| 経理規程・処理ルール集 | AIに渡す判断ルール | あるだけ | Word・Excel・PDF |
| 判断に使っている対応表など | 同上 | あるだけ | Excel など |

### 2-2. 「仕訳と証憑の対応」が一番の難所

過去の仕訳データはすぐ出ても、**どの仕訳がどのPDFから作られたか** が辿れないことがよくあります。

- 会計ソフトに証憑番号を入れている → 楽
- 共有フォルダに「取引先名_日付.pdf」で保存している → 名寄せスクリプトで対応付け、最後は目視
- 紙で保管 → 評価用の300件だけスキャンしてもらう

→ キックオフ直後に **「どうやって対応付けるか」を情シス・経理と相談** してください。ここで2〜3週間溶けることがあります。

### 2-3. データの安全な扱い

経理データには、取引先との契約金額、従業員の立替（氏名・口座）、個人事業主の情報が含まれます。

- [ ] データ取扱いの覚書（NDA・データ処理契約）を締結してから受け取る
- [ ] 受け渡しは顧客指定または合意した安全な方法で（メール添付でZIPを送らない）
- [ ] 保管場所、アクセスできる人、保管期限、終了時の削除方法を決めて記録する
- [ ] 個人情報（従業員名、個人取引先名、口座番号）は、必要に応じてマスキングする
- [ ] **外部のLLM API にデータを送ってよいか** を顧客と合意する（学習に使われない設定・契約か、データの保存場所はどこか）
- [ ] 送れない場合の代替（閉域環境で動くモデル、ローカルLLM）を検討する

> Algomatic はオープンなLLMを使った自社環境／オンプレミスでのLLM導入支援や、実務で使えるローカルLLMの検証記事を公開しています。
> 「クラウドLLMが使えない＝AI化できない」ではありません。

## 3. 「正解」を定義する

### 3-1. 過去の仕訳 ≠ 正解

過去の仕訳を正解として使うのが基本ですが、そのまま信じてはいけません。

| よくあるズレ | 例 | 対処 |
|---|---|---|
| 担当者ごとの揺れ | Aさんは「事務用品費」、Bさんは「消耗品費」 | どちらを正解とするか経理部長に決めてもらう |
| 単純な誤り | 税区分の付け間違い | 正解データから除外 or 修正 |
| ルール変更 | 期の途中で部門が統廃合された | 新ルール基準で正解を付け直す |
| 制度変更 | インボイス経過措置の控除割合が2026年10月に変更 | 期間ごとに正解を分けて扱う |
| 「どちらでも可」 | 会議費と福利厚生費の境界 | **許容リスト**（どちらも正解）として扱う |

LayerX は、学習・評価データのラベル誤りを **Confident Learning** という手法で自動的に見つけ、データの品質を改善する取り組みを公開しています。
手作業でも、「同じ取引先・似た明細なのに科目が違う」仕訳を抜き出して経理担当者に確認してもらうだけで、かなりのノイズが見つかります。

### 3-2. 正解確認会

評価データの中で怪しいもの（揺れ・誤りの疑い）をリストにして、**経理担当者と一緒に正解を決める会** を開きます。

- 1回60分で50〜100件が目安
- リストには「証憑の画像」「過去の仕訳」「疑問点」を並べておく
- 決まったルールは **「判断ルール集」** として文書化する（→ これがそのままAIに渡す知識になる）

```markdown
## 判断ルール集（みどり物産）
- R-001 事務用品通販B社の明細のうち、単価10万円未満の物品は「消耗品費」。10万円以上は経理担当に確認（要確認フラグ）
- R-002 会議中の飲食物は「会議費」、懇親会は「交際費」。区別がつかなければ要確認
- R-003 部門は、請求書の「ご注文者」欄の部署名から決める。記載がなければ発注一覧で確認
- R-004 個人の取引先への報酬（デザイン、原稿、士業）は源泉徴収あり。取引先マスタの「個人」フラグで判定
```

### 3-3. 「致命的な誤り」を決める

すべての誤りが同じ重さではありません。顧客と **誤りの重さのランク** を合意します。

| ランク | 例 | 影響 | 扱い |
|---|---|---|---|
| **致命的** | 金額の誤り、源泉徴収の漏れ、税区分の誤り（控除額が変わる）、取引先の取り違え | 納税額・支払額が変わる。監査で指摘 | **ほぼゼロを目指す。AIが怪しいと思ったら必ず人に回す** |
| 重大 | 勘定科目の誤り（費用と資産の取り違えなど） | 決算数値が変わる | 確認で必ず見つかる設計にする |
| 軽微 | 部門の誤り、補助科目の誤り、摘要の書き方 | 管理会計の数字が少しずれる | 月次で直せればよい |

## 4. 評価データセットを作る

### 4-1. 何件必要か

精度を測るときの誤差の目安（正解率90%前後のとき、95%信頼区間）：

| 評価件数 | 誤差の目安 | 使いどころ |
|---|---|---|
| 50件 | ±8ポイント | 開発中の素早い確認（スモークテスト） |
| 100件 | ±6ポイント | |
| **300件** | **±3.4ポイント** | **PoCの判断に使う本評価の目安** |
| 1,000件 | ±1.9ポイント | 本番前の最終確認、型ごとの細かい比較 |

→ 「85%と88%、どちらが良いか」を判断したいなら、300件はほしい。
→ 型ごとに精度を見たいなら、**型ごとに最低30〜50件**。

### 4-2. どう選ぶか（層化抽出）

ランダムに選ぶと、件数の多い簡単な型（型A）ばかりになり、難しい型が数件しか入りません。
**型ごとに件数を決めて選びます**（層化抽出）。

| 型 | 実際の件数比 | 評価データの件数 | 方針 |
|---|---|---|---|
| 明細多・毎回違う（型D） | 20% | 100 | PoC主対象なので多めに |
| 税率混在・按分（型C・H） | 8% | 60 | 主対象 |
| 取引先固定 | 32% | 40 | ルールで解けるかの確認用 |
| 毎月定額（型A） | 36% | 30 | 同上 |
| 特殊（型F・G・I） | 4% | 40 | 「要確認」にできるかの確認用 |
| 新規取引先 | — | 30 | 過去データなしでの性能 |
| **計** | | **300** | |

**選ぶときの注意**
- **期間を分ける**：例えば直近3か月を評価用、それ以前を「過去仕訳の参照用」にする。評価対象の仕訳そのものをAIが参照できると、**カンニング** になって精度が不当に高く出る
- [00 基礎](./00-basics.md#5-aiが間違えやすい仕訳チェックリスト) の「AIが間違えやすい仕訳」が全部入っているか確認する
- 証憑の画質（綺麗なPDF・スキャン・スマホ写真）も混ぜる

### 4-3. 評価データの形式

[tools/sample/ground_truth.csv](./tools/sample/ground_truth.csv) が見本です。**1行 = 1つの仕訳明細行** にします。

| 列 | 例 | 説明 |
|---|---|---|
| doc_id | INV-0001 | 証憑のID |
| line_no | 1 | 明細の行番号 |
| segment | 型D | 評価の集計単位（型） |
| account | 消耗品費 | 正解の勘定科目 |
| sub_account | 事務用品 | 正解の補助科目 |
| department | 営業部 | 正解の部門 |
| tax_category | 課税仕入10% | 正解の税区分 |
| amount | 12000 | 正解の金額 |
| acceptable_accounts | 消耗品費;事務用品費 | どちらでも正解とする科目（任意、`;`区切り） |
| note | | 正解確認会でのメモ |

## 5. 評価指標を決める

### 5-1. 指標の一覧

| 指標 | 計算式 | 何が分かるか |
|---|---|---|
| **項目別正解率** | 項目が正解の行数 ÷ 評価した行数 | どの項目（科目／部門／税区分／金額）が弱いか |
| **行の完全一致率** | 全項目が正解の行数 ÷ 評価した行数 | 「そのまま通せる」割合 |
| **証憑単位の完全一致率** | 全行が完全一致の証憑数 ÷ 証憑数 | 「請求書1枚まるごと直さなくてよい」割合。**業務効果に一番近い** |
| **カバレッジ（回答率）** | AIが「要確認」にしなかった行数 ÷ 全行数 | AIに任せられる量 |
| **回答した中での正解率（適合率）** | 回答した行のうち完全一致の行数 ÷ 回答した行数 | AIが自信を持って出した答えの信頼度 |
| **致命的誤り率** | 回答した行のうち致命的な誤りがある行数 ÷ 回答した行数 | **これが高いと使えない** |
| 処理時間 | 1証憑あたりの処理秒数 | 業務に乗るか |
| コスト | 1証憑あたりのAPI費用 | 費用対効果 |

### 5-2. カバレッジと正解率はトレードオフ

AIに「自信がないときは『要確認』にしていい」と許すと、

- 回答する量（カバレッジ）は **減る**
- 回答した中での正解率は **上がる**

```
       回答した中での正解率
  100% ┤●
       │  ●
   95% ┤     ●        ← この辺りで運用すると「AIが出した答えはほぼ信頼でき、
       │        ●         怪しいものだけ人が見る」状態
   90% ┤            ●
       │                 ●
   85% ┤                       ● ← 全部に答えさせた場合
       └┬────┬────┬────┬────┬──
        50%  60%  70%  80%  90% 100%  カバレッジ
```

**どこで運用するか** が、ビジネス上の判断ポイントです。
「全部答えて85%」より「70%に答えて97%正解、残り30%は人が見る」の方が、**確認の手間が減って業務は楽になる** ことが多いです。
（85%正解でも、どの15%が間違いか分からなければ、結局全部確認することになるため）

> Algomatic の品質保証の記事でも、AIに自信がないときは **「判断保留」** にして人に委ねる仕組みを紹介しています。

### 5-3. 平均だけ見ない（切り口を変えて見る）

LayerX は AI-OCR の精度を **様々な観点でモニタリング** し、ボトルネックを可視化して「勘ではなく事実に基づいて」改善するとしています。最低限、以下の切り口で集計します。

- 型（segment）別
- 項目別（科目・部門・税区分・金額）
- 取引先別（上位取引先、新規取引先）
- 証憑の品質別（綺麗なPDF / スキャン）
- 明細行数別

[tools/evaluate.py](./tools/evaluate.py) で、これらをまとめて出せます。

## 6. 合格基準を決める（PoC開始前に！）

PoC終了時に「本番化に進むか」を判断する基準を、**PoCを始める前に** 顧客と合意します。後から決めると、結果に合わせて基準を動かしたくなり、揉めます。

### 合格基準の例（みどり物産）

```markdown
## PoC合格基準（2026-10-28 合意）
評価データ：300件（直近3か月の請求書、型別に層化抽出）

### 必須（すべて満たすこと）
1. 致命的誤り率（AIが回答した行のうち）：1%以下
2. カバレッジ（要確認にしなかった行の割合）：60%以上
3. AIが回答した行の完全一致率：95%以上

### 目標（満たせば本番化の効果が大きい）
4. 証憑単位の完全一致率：70%以上
5. 型D（明細多）の行の完全一致率：90%以上
6. 処理時間：1証憑あたり60秒以内

### 効果試算の前提
- 上記を満たした場合、型C・D の処理時間が 1件平均6.1分 → 2.0分 になると試算
```

## 8. 注意点

- **カンニングに注意。** 評価対象の仕訳を、AIが参照する「過去仕訳」に含めない。期間で分けるのが一番安全。
- **正解を勝手に決めない。** 「たぶんこっちが正しい」で直さず、必ず経理担当者に確認する。
- **評価データは固定する。** 途中で入れ替えると、前回との比較ができなくなる。追加する場合はバージョンを分ける（v1, v2）。
- **評価データに過剰適合しない。** 評価データの誤りだけを狙って直していると、本番で同じ精度が出ない。開発用と評価用を分けるか、定期的に新しいデータで確認する。
- **制度変更の境目に注意。** 2026年10月のインボイス経過措置の変更をまたぐデータでは、同じ取引でも正解の税区分が変わりうる。
