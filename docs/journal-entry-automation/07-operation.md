# 07 運用・継続改善：使うほど賢くする

[← 目次へ](./README.md) ｜ 前：[06 本番実装](./06-implementation.md)

> **この章のゴール**
> - 本番稼働後に、何を・どの頻度で見ればよいか分かる
> - 人の修正を改善につなげるサイクルを回せる
> - 精度が落ちたときに、原因を順番に切り分けられる

---

## 1. 「使えば使うほど賢くなる」仕組み

LayerX は「AI Agent時代における『使えば使うほど賢くなるAI機能』の開発」で、次のような仕組みを紹介しています。

- ユーザーが負担なく修正できるUI（ドロップダウンでの候補表示）で、**構造化された修正データ** を集める
- そのデータを使って、**定期的にモデル・データを更新** する（パイプラインで自動化）
- 結果として、各社の使い方に合わせて精度が上がっていく

仕訳に当てはめると、毎日こういうデータが溜まります。

```
証憑ID / 明細 / AIの案（科目・部門・税区分）/ 人が確定した値 / 修正したか / 修正した人 / 日時
```

これは **本番の正解データ** そのものです。次のように使います。

| 使い方 | 頻度 | 内容 |
|---|---|---|
| 参照データの更新 | 毎日〜毎週 | 確定した仕訳を「過去の仕訳」として次の判断の参考に使う |
| 誤りパターンの発見 | 毎月 | 修正が多い取引先・明細・項目を集計して、エラー分析（[04](./04-poc.md#6-step-4エラー分析いちばん大事な作業)と同じやり方）|
| 判断ルール集の更新 | 毎月 | 繰り返し同じ修正がされている → ルールとして明文化する |
| 評価データセットの更新 | 四半期 | 新しい取引先・新しい書式の証憑を評価データに追加（新しいバージョンとして） |
| モデル・プロンプトの改善 | 必要に応じて | 改善 → 評価データで回帰テスト → リリース |

## 2. 何を見るか（監視する指標）

### 精度ダッシュボード

| 指標 | 意味 | 見るべき変化 |
|---|---|---|
| 修正率 | 自動OKにした行のうち、人が修正した割合 | 上がったら要注意（AIが自信を持って間違えている） |
| 要確認率 | 要確認に回った行の割合 | 上がると人の負担が増える。下がりすぎたら要確認の判定が甘くなっていないか確認 |
| 項目別の修正率 | 科目・部門・税区分・金額ごと | どこが崩れたか |
| 取引先別の修正率 | 修正が多い取引先トップ10 | 書式変更・取引内容の変化 |
| 処理件数・処理時間・費用 | 日次・月次 | 異常な増加 |
| エラー件数 | 読み取り失敗、API障害 | ゼロでない日の原因 |

### 業務KPI（キックオフで決めたもの）

| KPI | 頻度 |
|---|---|
| 1件あたりの処理時間 | 月次（四半期ごとに計測し直す） |
| 月次決算の締め日数 | 月次 |
| 月次チェックでの差し戻し件数 | 月次 |

**精度の指標だけでなく、業務KPIを必ず追う。** 精度が上がっても、締め日数が変わっていなければ、どこか別の場所にボトルネックがあります。

### 抜き取り検査

自動OKで通った行も、**毎月一定数（例：100件）を抜き取って人が見直します**。
人が確認を簡略化している部分の誤りは、修正率に現れないからです（気付かれないまま通っている可能性）。

## 3. 精度が落ちたときの切り分け手順

「AIの精度が落ちた」と言われたら、**いきなりプロンプトを直さない**。次の順で確認します。

```
1. 入力が変わっていないか？
   □ 特定の取引先の請求書の書式が変わった
   □ 新しい取引先が急に増えた
   □ スキャンの設定が変わった（解像度が下がった）
2. マスタ・ルールが変わっていないか？
   □ 科目・部門の追加・廃止・名称変更（組織変更、期首）
   □ 経理規程の変更
   □ マスタの同期が止まっている
3. 制度が変わっていないか？
   □ 税制改正（インボイス経過措置の控除割合、少額減価償却資産の閾値など）
   □ 電子帳簿保存法などの要件変更
4. システムが変わっていないか？
   □ プロンプト・モデルのバージョンが変わった（意図した変更 or 提供元の更新）
   □ 参照する過去仕訳の検索がおかしい
5. 正解の付け方が変わっていないか？
   □ 担当者が変わって、判断の仕方が変わった
6. ここまで問題なければ → AIの判断そのものの問題としてエラー分析
```

**多くの場合、原因は1〜3（入力・マスタ・制度の変化）** です。

## 4. 定期的なイベントへの備え

経理には毎年決まったタイミングでの変化があります。**年間カレンダーにして、事前に確認する** 運用にします。

| 時期 | イベント | AI側で確認すること |
|---|---|---|
| 期首 | 組織変更、科目・部門の追加 | マスタ同期、新しい部門の判断ルール |
| 決算月 | 決算整理仕訳、特殊な処理 | 対象外の処理が混ざらないか |
| 4月・10月 | 税制改正の施行が多い時期 | 税区分・閾値のルール更新、評価データの正解の見直し |
| 毎月月初 | 月次締め | この期間はリリース・メンテナンスをしない |
| 年末 | 取引先の請求書書式の変更が多い | 修正率の監視を強める |

---

## 5. 月次の定例（顧客との振り返り）

**アジェンダの例（30〜60分）**

1. 業務KPIの推移（処理時間、締め日数、差し戻し件数）
2. 精度指標の推移（修正率、要確認率）
3. 修正が多かったパターン上位3つと、対策（ルール追加・改善）
4. 判断ルール集に追加したい内容の確認（経理担当者に正解を決めてもらう）
5. 自動化レベルを上げられる対象の提案（例：3か月連続で修正ゼロの取引先は、確認を一覧での一括承認に）
6. 今後の予定（制度変更、組織変更、リリース予定）

## 6. 新人のタスク

- [ ] 精度ダッシュボードの月次確認とレポート作成
- [ ] 修正データの集計（修正が多い取引先・項目・パターン）
- [ ] 抜き取り検査の実施と記録
- [ ] 年間カレンダーの管理（制度変更・組織変更の事前確認）
- [ ] 月次定例の資料と議事録

---

## 7. 注意点

- **リリースして終わりにしない。** 放置すると、取引先・マスタ・制度の変化で精度は必ず落ちていく。
- **修正データをそのまま正解として学習に使わない。** 人の修正にも誤りやゆれがある。定期的にサンプルを確認し、怪しいものは経理担当者に確認する（[03](./03-data-and-eval.md#3-1-過去の仕訳--正解) と同じ）。
- **自動化レベルを上げるのは、データで根拠を示してから。** 「最近調子がいいから確認を減らそう」は危険。
- **顧客側の担当者が変わったら要注意。** 判断の仕方が変わり、修正データの傾向が変わる。引き継ぎ時に判断ルール集を使ってもらう。

- [ ] 精度ダッシュボードと業務KPIを毎月確認している
- [ ] 抜き取り検査を毎月実施している

- [ ] 年間カレンダーで制度変更・組織変更に備えている
- [ ] 月次定例で、改善と自動化レベルの見直しを行っている
