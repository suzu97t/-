# 社内ヘルプデスクの一次対応をどこまで自動化するか（15枚）

架空の事例で作った運営会議向けのデッキ。数値はすべて仮置きで、各ページの出典行に断りを入れてある。

- `deck.html` — 成果物。16:9（338.67mm × 190.5mm）、1 section = 1スライド、単体HTML
- `deck.pdf` — Chrome で印刷したPDF（15ページ）
- `build.py` — 生成スクリプト。パーツ集のCSSを流用し、本文を差し替える
- `diagrams.py` — 図（2×2・スイムレーン・アーキテクチャ・フローチャート）をインラインSVGで描く

## 使ったスキル

| スキル | 役割 |
| --- | --- |
| [consulting-pptx-skill](https://github.com/carnot-tech/consulting-pptx-skill) | デッキ全体の規約（`references/slide-rules.md`）、パーツ集、機械チェック |
| [diagram-design](https://github.com/cathrynlavery/diagram-design) | 図4枚の型・スキン・コネクタ規則・幾何チェック |

### 2つのスキルの突き合わせ

| 論点 | どちらに従ったか |
| --- | --- |
| 配色 | diagram-design の既定（白煙＋コーラル）は既存デッキから浮くので、デッキの暖色トークンを semantic role に割り当てた（`ink #322014`／`muted #8a7b6b`／`accent #5a3921`／`accent-tint rgba(90,57,33,0.10)`）。1図あたりの accent は2要素まで |
| 角丸 | slide-rules §5.1（正典）に従って箱は `rx=0`。フローチャートの開始記号だけは形が種類を表すので楕円を残した |
| 書体 | 図の文字もデッキの本文書体に揃えた（1デッキ2書体まで。§1）。CJKにはモノ体がないので、diagram-design のCJK規則どおり矢印ラベル・凡例も12単位のサンスで統一 |
| 文字の大きさ | 全幅の図は viewBox 1120×388。版面（306.67mm 幅）に対して12単位＝9.3ptになり、slide-rules §6 の「図解の中も9pt以上」を満たす |
| 背景 | ドット模様は使わない（diagram-design はスライド内では使うなと明記） |

## 作り方

```bash
# 1. パーツ集からたたき台を組む
python3 scripts/new_deck.py --parts b01,b02,m01,m05,b17,m08,m10,m12,m33,b09,b10 \
  --title "社内ヘルプデスク 一次対応の自動化" -o base.html

# 2. 本文と図を差し替える
python3 build.py

# 3. 機械チェック
python3 scripts/check_deck.py deck.html                 # 0 FAIL（consulting-pptx-skill）
node scripts/check_layout.mjs deck.html                 # layout OK（重なり・はみ出し）
python3 scripts/verify-geometry.py deck.html            # 0 findings（diagram-design のラベルマスク検査）

# 4. PDF化
chrome --headless --no-pdf-header-footer --print-to-pdf=deck.pdf deck.html
```

## 構成（15枚＝表紙＋本文13ページ＋裏表紙）

本文が10枚を超えるので、slide-rules §4.13 に従って冒頭に全体マップを置き、宣言した4区分を後続ページの右上にタグチップとして常設している。

| P | ページ | 見せ方 | 区分 |
| --- | --- | --- | --- |
| 1 | 対象の絞り込みと人の確認の残し方が、この資料の論点 | 全体マップ（→P.n 参照つき） | — |
| 2 | 一次対応は自動応答に置き換え、情報システム部は例外と承認に残る | 要約（現状→理由→打ち手の3段） | — |
| 3 | 初回の回答までの平均時間は7月に11.8時間まで伸び、1営業日を超えた | 縦棒＋含意 | 1 現状と対象 |
| 4 | 問い合わせの半分は、パスワード再発行と経費精算の差し戻しに集まる | 横棒（項目比較） | 1 現状と対象 |
| 5 | 件数が多く手順が定まった種別だけが、自動応答に向く | **図: 2×2（クアドラント）** | 1 現状と対象 |
| 6 | 自動応答は下書きまでを作り、送るのは担当者が確かめてから | **図: スイムレーン** | 2 仕組み |
| 7 | つくるのは自動応答と手順書の索引で、チャットは既存のまま | **図: アーキテクチャ** | 2 仕組み |
| 8 | 自動応答を入れた場合、一次対応の工数は月160時間から116時間まで減る | 増減ブリッジ | 3 効果と案 |
| 9 | 自動応答は初期費用が最も高いが、工数の削減幅と着手の早さで上回る | 比較表（5列） | 3 効果と案 |
| 10 | 対象と判断できない問い合わせは、自動応答が担当者に回す | **図: フローチャート＋右カラム** | 4 進め方と判断 |
| 11 | どのリスクも兆候が先に出るため、基準値を決めれば手を打てる | リスク表 | 4 進め方と判断 |
| 12 | 対象はパスワード再発行から始め、12月以降に経費精算の差し戻しへ広げる | ロードマップ（時間軸つき） | 4 進め方と判断 |
| 13 | 今週決めるのは、対象の種別、承認の権限、費用枠 | 軸のある表 | 4 進め方と判断 |

## 図の設計メモ

| 図 | 型 | ノード/項目 | 焦点（accent） | 意図した割り切り |
| --- | --- | --- | --- | --- |
| P.5 | 標準クアドラント（位置に意味がある） | 8項目 | 上位2種別のドット | 手順の定まりは担当者への聞き取りで、目盛りは持たない |
| P.6 | スイムレーン（3レーン） | 5工程・5矢印 | 担当者が確定する工程 | 対象外は破線1本で表し、担当者側の分岐は P.10 に譲った |
| P.7 | アーキテクチャ（ゾーン1つ） | 6ノード・6矢印 | 自動応答と下書きの矢印 | 問い合わせ管理システムは主張に効かないので落とした |
| P.10 | フローチャート | 5ノード・5矢印 | 自動応答が下書きを作る経路 | 終了記号と合流点は版面に入らないため省き、2つの終端で終える |
